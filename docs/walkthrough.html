Why it's built this way

It only does MAC, on purpose

Matrix-vector multiply is nothing but multiply-and-add: y[r] = Σ M[r][j]·v[j]. The 768×64 test is 49,152 MACs and nothing else. So instead of a general CPU, the chip is a row of MAC units (the PEs) plus just enough memory and control to keep them busy. Lecture 8 puts it as specialization plus parallelization.

SIMD: one instruction, many PEs

Single instruction, multiple data. On every repeat, every PE gets the identical PE instruction. The only difference between PEs is which 32-bit slice of the MEM0 word each one gets. More PEs just means a wider MEM0 and MEM2. And because every PE gets the same instruction, its wiring is one shared bus (handout section 3.4).

Lanes trade precision for speed

Each PE input is 32 bits. In INT32 that's one multiply per repeat. INT16 splits the same wires into 2 independent lanes, and INT8 into 4. Same hardware, 4× the work per repeat when the numbers are 8-bit. That's the quantization trend from lecture 8.

The sums stay put, the data streams past

Each accumulator lane is assigned one row of M for a whole block and keeps adding to it while the columns stream through, one column per repeat. Only when the block is done does the sum leave the PE (OUT, then WRITE). Accelerator papers call this an output-stationary dataflow.

Memory, datapath, control

Lecture 8's anatomy of an accelerator maps one to one: memory is the main buffer (MEM0, MEM1, MEM2), the datapath is the PE array, and control is the controller stepping through the instruction memory. Those are your three files: main_buffer.py, processing_element.py, accelerator.py.

Words this page uses

PE (processing element): one MAC unit with two registers, the accumulator and the output register.

Lane: one independent number inside a wider word. A 32-bit word in INT16 mode is 2 lanes of 16 bits. Lane 0 is the least significant (rightmost) one.

Slice: one PE's 32-bit share of a wide MEM0 or MEM2 word.

Port: where a memory's output appears (MEM0 and MEM1 output ports), or where MEM2's next input waits. In Python, these are plain attributes like _mem0_output_port.

Broadcast: sending the same value to every PE. That happens with the MEM1 word and with the PE instruction.

Accumulator: the register a PE adds products into. It's twice as wide as the inputs (64 bits) so sums don't overflow early.

Repeat: one pass of an instruction. Every instruction runs Count + 1 times.

Block: the group of rows the PEs work on together. Rows per block = PEs × lanes per PE.

MSB / LSB: most / least significant bit. Words on this page are always written with the MSB on the left, like ordinary numbers.

Clamp (saturate): replace a too-big value with the biggest value that fits, so +200 in 8 bits becomes +127.

Wrap: keep only the low bits, so +200 in 8 bits comes out as −56.

Sign extension: copying the sign bit into the new high bits when you widen a number, so −3 stays −3 (0xFD becomes 0xFFFD).

    Decoding the 9-bit instruction
    
    
    Three fields, left to right: opcode (2 bits), mode (2 bits), value (5 bits). Opcode 0 ("NO_VALUE") means the value field says which instruction it is. Opcode 1 means RND, and then the value field is the shift amount s.
    
    
    
    
    Mode codes: 00 = INT8, 01 = INT16, 10 = INT32. In Python: inst.get_opcode().uint, inst.get_value().uint, and inst.get_mode_bitwidth(), which hands you 8, 16 or 32 directly. Compare against the constants in instruction.py: PEI.NO_VALUE and PEI.RND for the opcode, PEI.MAC, PEI.NOP, PEI.OUT, PEI.PASS, PEI.CLR for the value.
    
    
    Trap: PEI.MAC == PEI.NO_VALUE == 0 and PEI.NOP == PEI.RND == 1. The same number means different things in different fields. Testing opcode == PEI.NOP is really testing for RND.
    

    
    Lanes: where each number lives
    
    
    Lane k of a word covers bits k·w through k·w + w − 1, counting bit 0 as the rightmost bit. Lane k of A pairs with lane k of B, goes into lane k of the accumulator, and comes out in lane k of the output. The accumulator lanes are wider (64 / lanes), so the output lanes are narrower than the accumulator's.
    
    
    
    
    
    
    Python's bitstring counts the other way. Hardware numbers bits from the right (bit 0 = LSB). bitstring indexes from the left (index 0 = MSB). So lane 0 of a 32-bit word is word[-w:] (the last w bits), not word[:w]. The friendly way out: word.cut(w) hands back the lanes left to right (lane n−1 first, lane 0 last), and Bits().join(pieces) puts pieces[0] on the left. If you cut with one and join with the other, in the same order, the lanes line up without any index arithmetic.

    Only OUT and CLR change the output register. Only MAC, PASS, CLR and RND change the accumulator.
    
    
    
      
    Why OUT clamps
    The result has to fit back into a w-bit lane of MEM2. Clamping gives the closest number that fits. Wrapping would give garbage: +40000 wrapped to 16 bits is −25536, so the sign flips.
    
      
    Why MAC doesn't
    The accumulator is the wide, temporary scratch space. Hardware adders just drop the carry out of the top. That's wrapping, and the spec asks for exactly that. Keep each lane's carry inside its lane.
    
      
    Why RND and PASS exist
    The compiler never emits them; they're for other programs, like the private tests. RND scales a wide sum back down by a power of two, which is how quantized ML hardware gets results back into a narrow format. PASS starts the accumulators from a value instead of zero.
    
    
    

    
    Rounding to nearest, ties to even
    
    
    Divide by 2s and pick the nearest integer. When the result is exactly halfway, pick the even neighbor: 2.5 → 2, 3.5 → 4, −2.5 → −2, −3.5 → −4. Anything not exactly halfway goes to the nearest: 3.75 → 4, −84.2 → −84.
    
    
    Do it with integers. A 64-bit accumulator can hold numbers a float can't represent exactly (anything past 253), so x / 2**s can be wrong before you even round. Python's round() does ties-to-even, but only after that float division. An exact method, for s ≥ 1:
    
    
      
      
    1. q = x >> s. In Python, >> on a negative int rounds toward −∞, so q is always the floor.
      2. 
      
    2. r = x − q·2s, the leftover. It's always between 0 and 2s − 1.
      3. 
      
    3. Compare r with half = 2s−1: below half, the answer is q; above half, q + 1; exactly half, whichever of q and q + 1 is even.
      4. 
    
    
    
    With s = 0 nothing changes. Try the "RND ties" example in the menu at the top of this page.
    

    
    What your code has to do
    
    
      
      
    1. execute_instruction(inst): read the opcode field. If it's PEI.RND, call _handle_rnd. Otherwise read the value field and call the matching handler. For NOP, do nothing.
      2. 
      
    2. Each handler, same skeleton: get w from inst.get_mode_bitwidth(). Work out the lane count (input width / w) and the accumulator and output lane widths from self._config. Split the registers you need into signed lane values. Compute each lane on its own. Pack the results back into one Bits of the full register width, keeping the lane order, and assign it to self._acc_value or self._output_value.
      3. 
      
    3. _handle_mac: acc lane + A lane × B lane, wrapped to the accumulator lane width.
      4. 
      
    4. _handle_out: clamp each accumulator lane to the output lane's range and pack into OUTPUT_BITWIDTH bits. Don't touch the accumulator.
      5. 
      
    5. _handle_pass: each A lane's value becomes that accumulator lane. Building Bits(int=value, length=wider) sign-extends for you.
      6. 
      
    6. _handle_clr: both registers become zero, each at its own width.
      7. 
      
    7. _handle_rnd: s = inst.get_value().uint; each accumulator lane becomes round-half-even(lane / 2s). The output stays as it is.
      8. 
    
    

    
    Traps
    
    
      
      
    • Bits(int=x, length=16) raises ValueError if x doesn't fit. A MAC can legitimately overflow its lane, so wrap first: reduce x modulo 2width, then build it with uint=, or convert back to signed. OUT has to clamp before building.
      • 
      
    • Lane values are signed (.int). The opcode, mode and value fields are unsigned (.uint).
      • 
      
    • Bits objects are immutable. You can't assign into a slice. Build a new one and reassign the attribute.
      • 
      
    • Never do the math on the whole 64-bit accumulator as one number in INT8 or INT16. A carry out of one lane would land in its neighbor.
      • 
      
    • PASS copies A (Data0, the MEM1 word), not B.

    The three operations
    
    
      
      
    • READ: the MEM0 port becomes MEM0[MemAOffset], the whole entry, in every mode. The MEM1 port depends on the mode:
        
        
          
      • INT32: MEM1[MemBOffset], as is.
        • 
          
      • INT16: entry MemBOffset[MSB:1]. MemBOffset[0] picks the half: 0 is the low half (lane 0), 1 is the high half. That half is repeated twice.
        • 
          
      • INT8: entry MemBOffset[MSB:2]. MemBOffset[1:0] picks one of four bytes, 0 being the lowest. That byte is repeated four times.
        • 
        
      • 
      
    • WRITE: MEM2[MemAOffset] = the MEM2 input port. MemBOffset is unused (the assembler sets it to 0).
      • 
      
    • NOP: nothing. The ports keep their old values.
      • 
    
    
    
    Opcode values: MI.READ = 0, MI.WRITE = 1, MI.NOP = 2. Mode codes: 0 = INT8, 1 = INT16, 2 = INT32. Mode.bitwidth(code) turns the code into 8, 16 or 32. WRITE and NOP carry mode 0 in their machine code, but it means nothing for them.
    

    
    Reading MemBOffset[MSB:1]
    
    
    That's Verilog's bit-slice notation. x[i:j] means bits i down to j, with bit 0 the rightmost. So:
    
    
      
      
    • x[MSB:1] is every bit except bit 0, the same as x >> 1 (or x // 2). x[0] is x & 1 (or x % 2).
      • 
      
    • x[MSB:2] is x >> 2 (or x // 4). x[1:0] is x & 3 (or x % 4).
      • 
    
    
    
    Turn the offset into an int with .uint first and use integer math. You could index the Bits directly, but its index 0 is the MSB, so bit 0 is offset[-1], and that's an easy place to slip.
    
    
    
    
    Look at the last column of each mode: offset j always lands on v[j]. That's the whole point of the design, next.
    

    
    Why READ works this way
    
    
    
      
    Every lane needs the same v[j]
    During a MAC, each lane is a different row of M, but they're all on the same column j, so they all need v[j] at the same moment. The buffer takes one w-bit element and copies it into every lane. In INT32 there's only one lane, so there's nothing to copy.
    
      
    Packing keeps MEM1 small
    The compiler packs 2 (INT16) or 4 (INT8) elements per MEM1 entry, which is why MEM1 is only 216−2 = 16,384 entries deep. In INT32 mode an offset of 16,384 or more would point past the end; staff said on Ed (#221) that out-of-range addresses won't be tested.
    
      
    The offset counts elements, not entries
    So the controller can step through v by adding 1 per repeat in every mode, and the buffer does the unpacking. The compiler reverses each group before packing so that v[0] sits in lane 0. That way "select bits = 0" lines up with "offset 0 = v[0]".
    
    
    

    
    What your code has to do
    
    
      
      
    1. execute_instruction(inst): read inst.get_opcode().uint. Call _handle_read for MI.READ and _handle_write for MI.WRITE. Do nothing for MI.NOP.
      2. 
      
    2. _handle_read: get both offsets as ints and the mode width. Set the MEM0 port to MEM0's entry at MemAOffset. For MEM1: work out how many elements share an entry (32 / w), which entry (the offset with its select bits dropped) and which lane (the select bits). Take that lane's bits out of the entry, repeat them to fill the 32-bit word, and set the MEM1 port.
      3. 
      
    3. _handle_write: store the MEM2 input port at MEM2[MemAOffset].
      4.

    • get_mode() gives the 2-bit code (0, 1, 2), not 8, 16 or 32. MemoryInstruction has no get_mode_bitwidth(); use Mode.bitwidth().
      • 
      
    • Lane 0 is the rightmost lane. In bitstring slicing that's the last w bits.
      • 
      
    • The repeated value must be exactly 32 bits (MEM1_BITWIDTH). In INT8 that's the byte four times.
      • 
      
    • READ sets both ports, every time, in every mode.
      • 
      
    • WRITE stores whatever the port holds right now. Getting the PE outputs onto the port is the controller's job, not the buffer's.
      • 
      
    • The public READ tests only ever select lane 0. READ INT16 130 26: 26 = 0b11010, select bit 0. READ INT8 130 24: 24 = 0b11000, select bits 00. A buffer that always takes the low lane passes both. (The full accelerator test would catch it, but write your own READ tests for the other lanes.)

      One repeat, step by step

        2. 
      
      2. Feed. Cut the MEM0 output port into PE_COUNT slices of INPUT_BITWIDTH bits. PE i gets slice i through input_b. Every PE gets the MEM1 output port through input_a.
        3. 
      
      3. PEs. Every PE executes the same PE instruction.
        4. 
      
      4. Collect. Join the PE outputs (get_output()), in the same order, into one word and put it on MEM2's input port with write_mem2_input, ready for a later WRITE.
        5. 
    
      
    
      Staff, on Ed #221: "Please follow the provided compiler's convention: READ supplies the operands to its paired PE operation, while WRITE is paired with a PE NOP. To prepare the PE output before writing it to memory, issue the necessary PE instructions paired with a memory NOP first, then issue WRITE. Combined WRITE + OUT does not have required behavior and will not be graded. Similarly, out-of-range addresses will not be tested."
      
    
      So memory first, then the PEs, is required: the READ's data has to reach the MAC in the same repeat. When you collect the outputs only matters for an instruction that pairs WRITE with OUT, and that won't be graded. Collecting at the end of every repeat, as above, works for every program the compiler writes.
      
    
      What happens with the wrong order
      
    
      If the PEs ran before the memory, every MAC would use the previous repeat's data. Here's the worked example both ways:
      
    
      

    
      Same position in, same position out
      
    
      The compiler packed each block's rows left to right across the MEM0 word, and extract_results_from_memory reads MEM2 left to right. So if PE 0 reads the leftmost slice of MEM0, its output has to land in the leftmost slice of MEM2. In bitstring terms: cut(INPUT_BITWIDTH) yields slices left to right, and Bits().join(outputs) puts outputs[0] on the left. Use them as a pair and the order takes care of itself. (Numbering PEs from the right would also work, as long as you do it in both places. Mixing the two puts results in the wrong order.)
      

    
      Why Count and the increments exist
      
    
      They're a loop built into the hardware. Without them, the program would need one instruction per column per block. With them, it's 4 instructions per block no matter how many columns there are. The INT16 public test is 24 instructions that expand to 402 repeats. The INT32 one is 240 instructions and 4,020 repeats. The instruction memory stays tiny, and that's what lets the controller stay simple.

        2. 
      
      2. Loop Count + 1 times, k = 0, 1, …, Count. Each time, build this repeat's memory instruction (same opcode and mode, offsets base + k × increment), then do the four steps above.
        3. 
      
      3. That's it. execute_instructions already calls you once per instruction.
        4. 
    
      

    
      Traps
      
    
        
      
      • Count is stored as repeats − 1. Loop Count + 1 times, not Count.

      • Every PE gets the same MEM1 word and the same PE instruction object. That's fine; PEs only read the instruction.

      Files, modules, imports
      Each .py file is a module. from src.compiler import f makes f usable by name. import numpy as np loads a whole module under a short name, so you write np.zeros(...). Inside src/, from .instruction import X (leading dot) means the file next door.
      
        
      Classes, objects, self

Functions defined inside a class are methods; Python passes the object as the first parameter, self.       Names starting with _

      @dataclass records

      Type hints
      x : int, -> Bits, list[Bits]: notes for humans and editors about what a value should be. Python never checks them when the program runs.
      
        
      Function arguments
      Defaults: def f(a, b=4). Keyword arguments: f(1, b=5), Bits(int=-3, length=8). Several results: return a, b returns a tuple, and x, y = f() unpacks it.
      
        
      Lists and comprehensions
      [] is an empty list, lst[i] an item, len(lst) the length, lst + [x] a new list with x added. [f(x) for x in xs] is a comprehension: a one-line loop that builds a list. for _ in range(n) is used when the loop variable isn't needed.
      
        
      Slicing and indexing
      a[i:j] is items i … j−1 (the end is never included). a[:j] starts at the beginning, a[i:] goes to the end, a[-1] is the last item. numpy 2-D: m[r0:r1, c] is rows r0 … r1−1 of column c. For a Bits, index 0 is the leftmost (most significant) bit.
      
        
      Text
      f"READ {x}" is an f-string: {x} is replaced by x's value. s.strip() trims spaces, .upper() uppercases, .split('|') cuts into a list, int('3') turns text into a number.
      
        
      Dictionaries
      A lookup table: d = {'READ': [0], 'WRITE': [1]}. d['READ'] is [0]; d.get('X') is None instead of an error when the key is missing.
      
        
      Errors
      raise ValueError('…') stops the program with a message. try: … except: … catches an error and does something else instead.
      
        
      Integer math
      / always gives a float (32/8 is 4.0); // is floor division; % is the remainder; >> and << shift (on negatives >> rounds toward −∞); & | are bitwise AND / OR; ** is power. Python ints never overflow: 2**100 is fine. A fixed width only exists where you create one, for example a Bits of a given length, which raises an error if the value doesn't fit.
      
        
      Bits (the bitstring library)
      Make one: Bits(int=-2, length=16) (signed), Bits(uint=5, length=8), Bits(hex='0x7f'), Bits(bin='0101'). Read it: .int, .uint, .hex, .bin, len(b). Cut it: b[0:16] (from the left), b.cut(16) (16-bit pieces, left to right). Combine: Bits().join([a, b]) or a + b (a on the left), b * 4 (b repeated). == compares every bit. A Bits never changes: make a new one instead.
