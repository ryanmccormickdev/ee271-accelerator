What you're building

What changes when Python becomes hardware

Time becomes explicit

In Python, one repetition of an instruction was one trip around a for loop, and it took no time. In hardware it's at least one clock cycle, and everything that happens is pinned to a cycle. A Python "repetition" becomes "the cycle in which the buffer gets READ 4 1, and the cycle after it, in which the PEs MAC its data".

State lives in registers

A Python attribute like self._acc_value becomes a flip-flop register. It only changes at a rising clock edge, and everything you compute in a cycle is the register's next value. Reading a register always gives the value from before the edge.

Memory answers a cycle later

Python's self._mem0[offset] returned at once. The SRAM model samples the address at a rising edge, and the word appears on its output in the next cycle. That single cycle of latency shapes the whole timing design.

Sixteen PEs, really at once

Python looped over self._pe_array. In hardware there are PE_COUNT physical copies of your PE, built by a generate loop, all computing in the same cycle. Nothing is sequential between them.

Every statement runs all the time

A Python function runs when called. A SystemVerilog assign or always_comb block is a piece of circuit: it is "running" continuously, and its output follows its inputs. The order you write blocks in doesn't matter.

Widths are fixed, and nothing raises

Bits(int=x, length=16) raised an error if x didn't fit. Hardware silently keeps the low bits. Signedness is a property of each expression, and getting it wrong gives a wrong number, not an exception.

The program arrives by handshake

execute_instructions(list) became an instruction memory with a program counter. Your controller asks for the next instruction by raising inst_exec_begins for one cycle, and has to keep up without leaving gaps.

The testbench is the host

The Python test called set_memory and get_mem2. Now a testbench loads the SRAMs before time 0 and dumps MEM2 at the end, by reaching into your design through fixed hierarchical names. If the names don't match, nothing compiles.

How to read this waveform

The run is the 6 × 3 matrix from the Part 1 walkthrough, M = [[1, 2, −1], [3, 0, 2], [−2, 1, 4], [0, −3, 1], [2, 2, 2], [−1, 4, 0]] times v = [2, −1, 3], in INT16 on 2 PEs. The answer is y = [−3, 12, 7, 6, 8, −6]. It was compiled and assembled by the staff tools with --pe_count 2, run through the staff equivalence testbench under Verilator, dumped to a VCD and converted cycle by cycle (docs/part2-rtl-src/vcd2json.py). MEM2 matched ivd-sim.

  • The testbench clock rises at 5, 15, 25, … ns. Cycle n is the period that ends with the rising edge at 10n + 5 ns. Each value shown is what the signal holds just before that edge, which is exactly what the flip-flops capture. Registers therefore change between one column and the next.
  • Cycles 0 to 4 are reset. Reset is released at 50 ns, in the middle of cycle 5.
  • Data buses are shown as signed INT16 lanes, most significant first. A bar | separates the two PEs' 32-bit slices: in [1 3 | −2 0], PE 0 has 1 and 3, PE 1 has −2 and 0. The hex view shows the raw bits.
  • remaining is the reference controller's repetition counter (repetitions left after this one). Your design may count differently. Everything else in the list is a port or a given signal, so your waveform should look the same if you use the same timing.
  • The recordings use Verilator with -fno-inline, which makes it agree with Icarus Verilog on every signal in every cycle (checked on this run). Without that flag Verilator skips the first instruction; see the last section.

One cycle of SRAM latency

The SRAM model (array.sv) samples its address at a rising edge and puts the word on q after that edge. So a READ issued in cycle t gets its data in cycle t + 1. In the run: the first READ (READ 0 0) is on buf_inst in cycle 7, the buffer presents MEM0 address 0 and MEM1 address 0 in cycle 7, and MEM0 q shows MEM0[0] = [1 3 | −2 0] in cycle 8.

Python's _handle_read filled the output ports at once, so READ and the MAC that used its data could happen in the same repetition. In hardware they can't be in the same cycle. That one fact is the reason for the timing of almost everything else on this page.

A subtlety: array.sv updates read_data with a blocking assignment in a clocked block, which can race with other flops that sample q at the same edge. In an event-driven simulator the extra latch block (q = read_data) runs one delta step later, so every flop sees the pre-edge value. Treat it as a normal synchronous SRAM, but see the Verilator caveat at the end of this tab.

Fetching instructions: the handshake and the prefetch

The instruction memory always shows inst = imem[program_counter] (it's an SRAM too, so that's the word at the address presented last cycle). When the controller takes an instruction, it raises inst_exec_begins for that one cycle. In that same cycle the instruction memory presents program_counter + 1 to its SRAM, so at the edge the counter moves on and the next instruction is fetched. Next cycle, inst already shows it.

So a new instruction can start every cycle. In cycle 6 the CLR has one repetition, it's the last, and the controller takes READ|MAC at the same time: inst_exec_begins is high in cycles 5 and 6 back to back.

Why the PE instruction runs one cycle after its memory instruction

A READ|MAC repetition has two halves that need different cycles. The buffer must see the READ in cycle t so the address reaches the SRAM; the PEs must do the MAC in cycle t + 1, when the data is on matrix_data and vector_data. The reference controller issues buf_inst straight from its registers and passes the PE half through one more register, so pe_inst is a one-cycle-delayed copy. Look at cycles 7 to 10: buf_inst is READ 0 0, READ 1 1, READ 2 2, NOP, and pe_inst is CLR, MAC, MAC, MAC, each one cycle behind its partner.

Every PE instruction is delayed, not just MAC. That keeps each instruction's two halves paired: CLR (with NOP) and OUT (with NOP) also reach the PEs one cycle after their memory halves. Bug 1 in the menu above removes the delay; select it to see the MAC use the previous repetition's data.

OUT, then WRITE: why the WRITE commits a cycle later

Each tile ends with NOP | OUT then WRITE | NOP (compiler.py lines 90–91). With the PE half delayed, the OUT runs on the PEs in the same cycle the WRITE is on buf_inst: cycle 11 in the run. The output registers only change at the end of cycle 11. If the WRITE stored output_data in cycle 11, it would store the old outputs (zeros, from the CLR). So the buffer remembers the WRITE for one cycle and commits it at the end of cycle 12, when output_data holds the OUT's result: gwen = 0, a = 0, d = [−3 12 | 7 6].

Bug 2 is a buffer that writes in the WRITE's own cycle. Every row of MEM2 comes out as zeros. (Other fixes exist: the controller could delay the WRITE itself. What matters is that the WRITE samples the outputs after the OUT.)

Back to back, zero bubbles

A bubble is a cycle in which nothing new is issued. The reference controller takes the next instruction in the last cycle of the current one, so the buffer gets a new repetition every cycle from cycle 6 to cycle 18. The whole run is 13 repetitions: 2 tiles × (1 CLR + 3 READ|MAC + 1 OUT + 1 WRITE) + 1 padding.

Why this matters so much in Part 3: the figure of merit is FoM = (Tint8 + Tint16 + Tint32)2.3 × area × power × 10−15, with T = cycles × clock period. The time enters with an exponent of 2.3. One bubble per instruction (Bug 6) still gives correct results but adds 64 cycles to each official test; one bubble per repetition would nearly double the time.

The ratio holds area, power and the clock period fixed, so it's (Tnew / Told)2.3. Cycle counts come from the model below, which matches every measured run. The 2.3 is from the Part 3 handout, section 2.1.

How the run ends: the padding instruction and the end condition

  • The Makefile passes INST_COUNT = (lines in mat_mul.asm) + 1, here 9. ivd-as pads inst.bits with all-zero words, so instruction 8 is all zeros, which decodes as READ INT8 0 0 | MAC INT8 with count 0: one repetition. The controller takes it in cycle 17, issues its READ in cycle 18, and the PEs run its MAC in cycle 19. It changes the accumulators after the last WRITE, so the results don't care. ivd-sim stops at the first all-zero word and never runs it.
  • In cycle 18, program_counter reaches 9 = instruction_count, so inst_valid drops. In cycle 19 the controller is IDLE (buf_inst_valid = 0) but pe_inst_valid is still 1. In cycle 20 everything is 0.
  • The testbench's simulation_complete = program_counter == instruction_count && !pe_inst_valid && !buf_inst_valid rises at 195 ns. It waits one more period, prints the cycle count and dumps MEM2 at 205 ns.
  • So your last WRITE must be in MEM2 by then. A deeper pipeline (Part 3) must keep a valid signal high until its last write has committed, or the dump happens first.

Counting cycles

The testbench prints $time / 10 at the dump: "Computation took 20 clock cycles". That's cycles 0 to 19: 5 of reset, 1 to take the first instruction (cycle 5), 13 repetitions (cycles 6 to 18), and 1 for the last PE instruction to drain (cycle 19). In general, with a zero-bubble design like this one:

Six ways to get the timing wrong

Each of these is the reference design with one deliberate bug, recorded on the same program and run on all three official tests. Pick one in the Design menu at the top to see its waveform, with every value that differs from the correct design marked. "Seed 7" reruns the test with vector seed 7 instead of 12345.

Two of these pass the official tests. The INT16 test's vector ends in 0 and the INT32 test's ends in −1 (0xFFFFFFFF, whose four bytes are identical), so a bug that only spoils the last column's product is invisible there. INT8 is the only official test where OUT clamps anything (801 of its 1,024 outputs; INT16 and INT32 never clamp). Run other seeds too (the repo's make eq-stress).

Same design, different waveform: the Verilator race

Pick "Correct design, Verilator default flags" in the menu. It's the same reference design, simulated by Verilator without -fno-inline. In cycle 6 the buffer already gets READ 0 0: the CLR was never executed. At the end, an extra all-zero instruction runs (two padding READs, cycles 17 and 18). MEM2 and the cycle count are the same as the correct run, so the equivalence tests can't tell.

What happened: Verilator inlines the instruction memory's array, sees that its cen is the constant 0, and turns the output latch into a plain alias of read_data. read_data is updated with a blocking assignment at the rising edge, so a controller flop that loads inst directly (cur <= inst;, in a style like the reference's) sees the word fetched at that edge, one instruction ahead. Icarus, and Verilator with -fno-inline or -O0, keep the latch as a separate step and give the event-driven answer. We expect VCS to behave like Icarus but could not check it here.

When it bites: programs whose first instruction matters. Under default Verilator flags, the staff's tb_pe program (MAC once, OUT once) runs OUT first, so the PE's output stays 0, and tb_buffer_wb's only instruction (WRITE 3) never happens. Whether you see it depends on how your controller is written. The repo's make targets default to Icarus, and SIM=verilator builds with -O2 -fno-inline; add -fno-inline whenever you run Verilator by hand.

Lanes are bit slices

    
Lane k of a w-bit lane layout is bits k·w through k·w + w − 1. In SystemVerilog that's the indexed part-select x[k*w +: w]: "w bits starting at bit k·w, going up". The accumulator lane is twice as wide as the input lane, so in INT8 the four accumulator lanes are acc[16*k +: 16]. Hardware counts bits from the right, like this page, so no index flipping is needed (unlike bitstring in Part 1).

    

    

    
A loop like for (int k = 0; k < 4; k++) inside always_comb is fine: it's unrolled into four copies of the circuit. But the range form x[8*k+7 : 8*k] is illegal when k is a variable, even though it means the same thing. Both Icarus and Verilator reject it; Verilator even suggests +:.


    
Signed arithmetic, for Python programmers

    
In Python an int is just a number. In SystemVerilog every expression has a width and a signedness, decided by rules that surprise everyone once. These are the ones that matter for the PE, each checked in both Icarus and Verilator:

    
    
      
  1. Vectors are unsigned unless declared signed. logic [15:0] x holding 0xFFF0 is 65,520, not −16.
    2. 
      
  2. A part-select is always unsigned, even of a signed vector: acc[15:0] and x[8*k +: 8] are unsigned. $signed(...) reinterprets the bits as signed (it doesn't change them).
    3. 
      
  3. One unsigned operand makes the whole expression unsigned. Then every operand is zero-extended to the expression width, including the ones you wrapped in $signed.
    4. 
      
  4. Widths are context-determined. The operands of + - *  and of a comparison are first extended to the widest of all of them and of the left-hand side, then the operation is done at that width. Concatenations {} are self-determined: {a + b} stays at the operand width and loses the carry.
    5. 
      
  5. Comparisons follow the same rule. $signed(lane) > 8'h7F is an unsigned comparison because 8'h7F is unsigned, so −200 > 127 is true. Compare with 127 (a signed 32-bit integer) or 8'sd127.
    6. 
      
  6. >>> is an arithmetic shift only on a signed operand. x >>> 2 with an unsigned x shifts in zeros, like >>.

Each instruction, as a circuit

    

      
MAC
Per lane, a signed multiplier and an adder: four 8 × 8 multipliers (16-bit products) in INT8, two 16 × 16 (32-bit) in INT16, one 32 × 32 (64-bit) in INT32. Each product goes into its own wide accumulator lane, and the lane's adder simply drops any carry out of the top: that's the "wrap" the spec asks for (Ed #226: overflow isn't tested). The mode picks which set of results becomes the next accumulator. Part 3 points out that the small multipliers can be built from the large ones (handout 2.2.1).

      
OUT: compare and select
Per lane, the accumulator lane is compared with the two limits and one of three values is chosen: the lower limit, the upper limit, or the low w bits of the lane. An equivalent test without comparators: a lane fits in w bits exactly when all the bits above bit w − 1 are copies of bit w − 1. If not, the sign bit says which limit. The accumulator's next value is itself (OUT doesn't change it).

      
PASS: sign extension
No arithmetic at all: each A lane's sign bit is copied into the upper half of the accumulator lane. In SystemVerilog, {{8{a[7]}}, a[7:0]} is the 16-bit sign extension of a byte, or assign the byte to a logic signed [15:0] after a $signed.

      
CLR, NOP and the valid
CLR: both next values are 0. NOP: both next values are the current values (the register holds). And whenever pe_inst_valid is 0, it's a NOP regardless of the bits, which matters because the controller's registers hold stale instructions between programs (look at cycle 0 to 5 of the waveform: pe_inst shows MAC, with valid 0).

      
RND: shift, then decide
Per lane: q = x >>> s (an arithmetic shift, so q = floor(x / 2s)). The bits shifted out decide the rounding: the guard bit g = x[s − 1], the sticky bit st = OR of x[s − 2 : 0], and the lsb of q. Round up when g and (st or lsb). The demo below shows the bits.

      
Encodings with no meaning
Opcodes 2 and 3, values 5 to 31 with opcode 0, and mode 3 have no defined behavior and aren't graded (Ed #238). The staff Python raises an error for the unknown opcodes and values; the simplest hardware treats them as NOP.

    


    
RND at the bit level

    
Pick a lane width, a value and s. The rule from the handout is "divide by 2s, round to nearest, ties to even". In bits: the low s bits are the remainder r (always 0 … 2s − 1, because the shift rounds toward −∞), the top bit of r is the guard bit, the rest is sticky.

    

    
For s larger than the lane width, the bits above the lane are copies of the sign bit; they're shown faded. With s = 0 nothing is shifted and nothing changes.


    
The register pattern: next state in always_comb, register in always_ff

    
A tidy way to write any block with registers: compute every register's next value in an always_comb block (start by assigning "hold", so nothing is left unassigned), and copy it into the register in a tiny always_ff with the asynchronous active-low reset. This idiom is the shape, not a PE:


always_comb begin
    acc_d = acc_q;                    // default: hold (this line also prevents a latch)
    if (pe_inst_valid && is_clr)      // one of your decoded conditions
        acc_d = '0;
end

always_ff @(posedge clk, negedge rst_n) begin
    if (!rst_n) acc_q <= '0;          // asynchronous, active-low reset
    else        acc_q <= acc_d;
end

    
_q for a register and _d (or _n, _next) for its next value is a common naming habit; it makes waveforms easier to read.

vector_decoder: two addresses, one mode

    
defines.sv provides vector_decoder (see it in the code reader). Its two address inputs exist because the address and the lane select are needed in different cycles: addr_from_controller is used to compute addr_to_mem (cycle t), and addr_from_controller_reg to pick the lane (cycle t + 1, from a register). Two details to plan for:

    
    
      
  • It has a single mode input, used for both jobs. In cycle t + 1 the controller is already presenting the next instruction, and when that's the NOP | OUT after the last READ, its mode field is 0 (INT8), because the assembler only fills in the mode for READ (assembler.py, convert_mem_instruction: only the READ branch calls set_mode, line 98). So the mode used for the lane select must be the READ's mode, kept from cycle t too. The reference uses two decoder instances: one with this cycle's offset and mode for the address, one with the registered offset and mode for the data. (One decoder with the registered values for both also works only if the address side never needs the new mode.)
    • 
      
  • It has no default in its case (mode), so for mode 3 nothing is assigned. In simulation that just holds the old value; in synthesis it describes a latch. Yosys refuses the file for that reason ("Latch inferred ... from always_comb process"); Verilator's lint reports CASEINCOMPLETE. Mode 3 never occurs, so the behavior doesn't matter, but expect a warning from synthesis.
    • 
    

    
Bug 4, measured: decoding the data with this cycle's mode instead of the READ's mode spoils the last MAC of every INT16 and INT32 row tile. It passes all three official tests (the INT16 vector ends in 0, the INT32 one in −1) and fails INT16 and INT32 with vector seed 7: 16 of 16 MEM2 rows wrong. In the worked example it turns y = [−3 12 7 6 8 −6] into [0 6 −5 3 2 −6]. 


    
WRITE

    
A WRITE stores all of output_data (every PE's output register side by side) at MEM2 address mema_offset. In hardware: pull write_control_n low for exactly one cycle with the address on a and output_data on d. The SRAM commits at the end of that cycle. Which cycle is the timing question: it must be a cycle in which output_data already holds the result of the OUT that came before the WRITE. In the reference, the WRITE is issued in cycle t and committed at the end of t + 1 (cycles 11 and 12 in the run). memb_offset is unused (the assembler sets it to 0), and so is the mode.


    
What the buffer has to remember

    
Python's buffer was stateless apart from its ports. A hardware buffer has to carry information from the cycle an instruction arrives to the cycle its effect happens: the READ's offset and mode (for the lane select), and a pending WRITE with its address (if, like the reference, the buffer delays the write). Each is a small register with a reset.


    
Buffer traps

    
    
      
  • Selecting the MEM1 lane with the live offset (Bug 3): passes INT32, fails INT8 and INT16.
    • 
      
  • Selecting it with the live mode (Bug 4): passes all three official tests.
    • 
      
  • Writing MEM2 in the WRITE's issue cycle (Bug 2): every row is zero.
    • 
      
  • Forgetting buf_inst_valid: during reset and after the program, buf_inst holds whatever the controller's registers hold (all zeros = READ INT8 0 0). A buffer that ignores the valid reads constantly; one that ignores it for WRITE could write garbage.
    • 
      
  • Renaming u_matrix_mem, u_vector_mem or u_output_mem: the testbench no longer compiles.
    • 
      
  • The address port of MEM1 is 14 bits; the offsets are 16. Take the right slice (the decoder does).

Two states

    
IDLE: nothing is being executed; take inst as soon as inst_valid is 1. EXECUTING: one repetition goes out every cycle. On the last repetition, if another instruction is valid, take it in the same cycle and stay in EXECUTING; otherwise go back to IDLE. In the worked example the controller is IDLE in cycle 5 only (and again from 19), and EXECUTING for 13 cycles in a row.


    
Count + 1 repetitions

    
The assembler stores the written count minus one, so the hardware runs inst.count + 1 repetitions, just as in Part 1. A natural circuit: load a down-counter with count when you take the instruction, and the repetition is the last one when the counter reads 0. Then CLR, OUT and WRITE (count 0) take exactly one cycle and are "last" in their first cycle. (An up-counter compared with count works the same.)


    
Offsets

    
Load the two offset registers with the instruction's mema_offset and memb_offset, and add mema_inc and memb_inc (1 bit each) after every repetition. buf_inst carries the opcode and mode from the instruction and the offsets from these registers. In the run: READ 0 0, READ 1 1, READ 2 2, then tile 1's READ 3 0, READ 4 1, READ 5 2.


    
The handshake

    
Raise inst_exec_begins in exactly the cycles you take an instruction. The instruction memory then increments its counter at the end of that cycle and has already started fetching the next word, so inst is the next instruction one cycle later. Raising it in a cycle where you don't take inst skips an instruction; forgetting it stalls the program on the same instruction. It's typically a combinational signal of the state, the counter and inst_valid.


    
Zero bubbles

    
Taking the next instruction on the last repetition, not after it, is what makes the issue back to back. The alternative, going through IDLE after every instruction, costs a cycle per instruction: Bug 6 in the Cycles tab, 28 cycles instead of 20 for the example and +64 for each official test.


    
The delayed PE instruction

    
The buffer needs a repetition one cycle before the PEs do (the SRAM latency). In the reference the controller drives buf_inst from its registers and puts pe_inst / pe_inst_valid through one extra register, so the PE half of every repetition arrives one cycle later. Another place for that delay would be the buffer or the PE itself; what matters is that each PE operation meets its READ's data.


    
The end of the program

    
When program_counter reaches instruction_count, inst_valid goes to 0 and stays there. The controller finishes the last instruction's repetitions, goes to IDLE, and its valids drop: buf_inst_valid first, pe_inst_valid a cycle later. That's the testbench's signal to wait one cycle and dump MEM2.


    
Controller traps

    
    
      
  • Running count repetitions instead of count + 1.
    • 
      
  • Holding inst_exec_begins high for more than one cycle per instruction, or raising it in reset.
    • 
      
  • Stepping the offsets after the first repetition is issued instead of after each one, or not reloading them for a new instruction.
    • 
      
  • Driving pe_inst in the same cycle as buf_inst (Bug 1): every MAC uses the previous repetition's data. It passes the INT16 test under Verilator.
    • 
      
  • Leaving a valid high after the program, so the testbench never finishes (it times out after 1,000,000 cycles with no MEM2 dump).
    • 
      
  • The state enum is 2-state, so a missing reset of state won't show in any simulator. Reset it anyway.

Same position in, same position out

    
The compiler packs a tile's rows into the MEM0 word left to right: the first rows go in the most significant slice. extract_results_from_memory reads MEM2 left to right too. So the PE that reads the leftmost 32 bits of matrix_data must write the leftmost 32 bits of output_data. The reference numbers PEs like Python's cut(): PE i uses bits [32·(P−1−i) +: 32] on both buses. Numbering from the right works too, as long as both buses use the same numbering. Bug 5 mixes them: in the worked example MEM2[0] becomes [7 6 −3 12] instead of [−3 12 7 6], and all 16 rows of every official test are wrong.

What the official tests can and can't see

    

    
    
      
  • Only INT8 exercises clamping. A PE that truncates instead of clamping fails int8_test at once and passes the other two.

X hides in Verilator. Bug 1 (PE instruction not delayed) passes int16_test under Verilator. Under Icarus it fails: the first MAC reads the SRAM output before anything was ever read, which is X, and MEM2 row 0 comes out as 512 x characters. A 4-state simulator (like VCS) catches what Verilator can't show.

    
The race. With default flags Verilator lets a flop that loads the instruction memory's output directly see the word fetched at that same edge, so the controller starts one instruction late: the first instruction is skipped and one all-zero word runs at the end. For the compiled programs that's invisible (the first instruction is a CLR after reset), but tb_pe and tb_buffer_wb show it. -fno-inline (or -O0) makes Verilator agree with Icarus on every signal, every cycle (checked on the worked example). 

    
A glitch in the end detector. The testbench waits for @(posedge simulation_complete), and simulation_complete is combinational. If, while program_counter == instruction_count, one valid falls at the same edge another rises, an event-driven simulator can see a zero-width 1 in between, and the dump starts early. Our Bug 6 (bubbles) does exactly that near its end: Icarus reports 27 cycles on the worked example and Verilator 28, and 16,503 vs 16,504 on the official INT8 test (all measured; MEM2 is right in every case, because the last WRITE had already committed). If your two simulators disagree by a cycle or so, look for this before anything else, and in Part 3 make sure no such edge exists before your last write is in MEM2.

    
Very small PE counts. With 4 PEs, the INT8 1024 × 1024 test can't even be generated: the staff ivd-sim steps mema_offset once more after the last repetition, to 64 × 1,024 = 65,536, which doesn't fit its 16 bits (checked: ValueError: 65536 is too large an unsigned integer for a bitstring of length 16; the calculator in the Cycles tab flags it). So 5 is the smallest PE count for the INT8 test, and below 16 PEs the instruction memory must also be deeper than 128.

SystemVerilog for Python programmers

    
Only what this project uses. The mental shift: you're not writing steps for a processor, you're describing wires and registers that all exist at once.

    

      
module = a circuit with ports
module pe(input logic clk, output logic [31:0] y); ... endmodule. An instance (pe u_pe (.clk(clk), .y(out));) is one physical copy. Connect by name with .port(signal). No return values, no calls.

      
logic and widths
logic [31:0] x; is a 32-bit vector, bit 31 on the left. logic signed [15:0] is signed. A width is part of every signal and constant; there's no "just an int" in hardware (int exists, but it's a 32-bit signed 2-state variable, best kept to loop counters).

      
assign: a wire with an equation
assign y = a & b; means y is always a AND b. Change a, and y changes. There's no order between assigns.

      
always_comb: combinational logic with if and case
A block that recomputes its outputs whenever an input changes. Assign every output on every path, or you describe a latch. Use = inside it. Think "a function evaluated continuously", not "code that runs once".

      
always_ff: registers
always_ff @(posedge clk, negedge rst_n): the outputs change only at a rising clock edge (or immediately on reset). Use <= inside it. Everything assigned here is a flip-flop.

      
= vs <=
<= (non-blocking): all right-hand sides are read first, then all registers update together, like a real clock edge. = (blocking) updates at once, so later lines see the new value. A two-stage delay line written with = in a clocked block collapses into one stage: the second register becomes a copy of the first (checked in Icarus and Verilator).

      
Literals
8'hFF (8-bit hex), 4'b1010, 16'd5, 8'sd127 (signed). '0 / '1 fill any width. An unsized 5 is a 32-bit signed integer.

      
Selecting bits
x[7:0] bits 7 down to 0. x[3] one bit. x[8*k +: 8] 8 bits upward from bit 8k (k may be a variable; the width can't). All part-selects are unsigned.

      
Concatenation and replication
{a, b} puts a on the left (like a + b for bitstring). {4{byte}} repeats it four times (like byte * 4). The result is unsigned.

      
Packed structs and enums
pe_inst_t is a 9-bit vector with field names: pe_inst.opcode is bits [8:7]. The first field is the most significant. typedef enum {IDLE, EXECUTING} names values (and defaults to a 2-state int).

      
if, case, ?:
Inside always blocks: if / else, case (x) 2'd0: ...; default: ...; endcase. Anywhere: c ? a : b. They describe multiplexers.

      
for loops and generate
A for inside always_comb is unrolled into copies of logic. A generate for with a genvar makes copies of instances (the PE array).

      
`define, `include, parameter
`include "defines.sv" pastes a file. `define W 32 makes a text macro used as `W. A parameter is a typed per-module constant, settable per instance with #(.W(16)).

      
Simulation-only code
initial, #10 delays, $display, $readmemb, $finish, string and tasks with delays belong in testbenches. Synthesis ignores or rejects them.

      
Hierarchical names
dut.u_buffer.u_output_mem.dumpmem(...) reaches into any instance from anywhere. Testbenches rely on it; don't use it in design code.

      
X and Z
In a 4-state simulator, a bit can be X (unknown) or Z (undriven). Uninitialized registers start at X, and X spreads through arithmetic. Verilator has no X: it uses 0. Reset everything that matters.

    


    
Traps, all in one place

    
    
      
  • A comment that starts with "verilator". Verilator reads any comment whose first word is verilator, in any capitalization and in both // and /* */ form, as a pragma, and stops with %Error-BADVLTPRAGMA: Unknown verilator comment. Checked: // verilator is used locally, // Verilator is used locally and /* verilator is fast */ all fail; // we use verilator locally is fine. Put another word first.
    • 
      
  • Latches from an incomplete if or case in always_comb. If some path leaves an output unassigned, the output must remember its old value: a latch. Verilator's lint reports CASEINCOMPLETE and LATCH; Yosys stops with "Latch inferred for signal ... from always_comb process" (both checked). Fix: assign defaults at the top of the block, or add a default.
    • 
      
  • Blocking assignments in always_ff. = in a clocked block makes later lines see new values in the same cycle (a delay line collapses) and can race with other blocks. Use <= for registers, = in always_comb.
    • 
      
  • X from a missing reset. A register without a reset is X in VCS and Icarus until something assigns it, and any arithmetic with X gives X. Verilator shows 0 instead, so the bug passes locally (checked with a counter: Icarus prints xxxxxxxx, Verilator counts from 0).
    • 
      
  • Widths. Adding two 8-bit values in an 8-bit context drops the carry; a 64-bit product assigned to 32 bits is truncated; an unsized constant is 32 bits. make lint prints WIDTH warnings for these; the equivalence build hides them.
    • 
      
  • Signedness. One unsigned operand (part-select, concatenation, unsigned literal) makes the whole expression unsigned and zero-extends everything. See the .
    • 
      
  • Variable part-selects. x[8*k+7 : 8*k] with a variable k is illegal; use x[8*k +: 8].
    • 
      
  • int and integer. for (int k = 0; ...) in always_comb is fine. But a generate loop needs a genvar, an int signal is 2-state and signed (it hides X and makes mixed expressions signed), and a module-level integer shared by several blocks is a race (array.sv's loadaddr uses the wrong one).
    • 
      
  • Hierarchical names. The testbench needs u_buffer, the three array names, pe_inst_valid and buf_inst_valid exactly.
    • 
      
  • The Verilator race. Without -fno-inline, Verilator can make your controller take the instruction one ahead and skip the first one. See .
    • 
      
  • The tool environment. ivd-as crashes with bitstring 5 (AttributeError: 'Bits' object has no attribute 'length'); the Part 2 environment needs bitstring<5. And ivd-as silently truncates programs longer than the instruction memory depth.
    • 
      
  • check_results.sh always exits 0. Read the PASSED / FAILED line; don't trust make's exit status.

Words this page uses

    

      
RTL (register-transfer level): describing hardware as registers and the logic between them. What you write in Part 2.
Cycle: one clock period. Here: the period ending with the rising edge at 10n + 5 ns.
Rising edge: the moment clk goes 0 → 1, when every flip-flop captures its input.

      
Register / flip-flop: storage that updates only at a clock edge.
Combinational: logic with no memory; its output follows its inputs.
Latch: storage that is transparent while an enable is active. Usually a mistake in your logic.

      
Asynchronous active-low reset: a reset input that acts immediately (not at an edge) when it's 0. rst_n.
Valid: a 1-bit signal saying "the data next to me means something this cycle".
Handshake: a protocol between two blocks; here, inst_exec_begins saying "taken".

      
Latency: cycles between asking and getting. The SRAM's read latency is 1.
Pipeline: splitting work over several cycles so a new item can start every cycle. The buffer and the PEs form a two-stage pipeline.
Bubble: a cycle in which a pipeline stage gets nothing new.

      
Prefetch: fetching the next instruction before it's needed (the instruction memory's program_counter + 1).
Repetition: one of the count + 1 passes of an instruction.
Tile: a block of output rows the PEs compute together: PEs × lanes rows. Each tile ends in one MEM2 word.

      
Lane: one independent number inside a wider word.
Part-select: a range of bits, x[7:0] or x[k*8 +: 8].
Sign extension: widening a signed number by copying its sign bit.

      
Testbench: simulation-only code that drives your design and watches it.
Hierarchical name: a path like dut.u_buffer.u_output_mem to any instance or signal.
VCD / VPD: waveform file formats (open VCD with Surfer; VPD is VCS's, for DVE).

      
2-state / 4-state: whether a simulator has only 0 and 1 (Verilator) or also X and Z (VCS, Icarus).
Race: a result that depends on the order the simulator happens to run things in.
Black box: a module synthesis treats as empty (the SRAMs).

      
Equivalence test: run the RTL and the Python on the same input and compare MEM2 bit for bit.
FoM (figure of merit): Part 3's score, (total time)2.3 × area × power × 10−15. Lower is better.
Lint: a static check for suspicious code.
