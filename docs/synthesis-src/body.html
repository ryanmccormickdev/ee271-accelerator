What the course takes from it

Quiz yourself

Which two programs does make synthesize run, and why the first one?

ivd-gv generates defines.sv (widths, PE count, the instruction structs, the vector_decoder module) with all defaults, then dc_shell-t runs dc_synth.tcl. Every RTL file `includes defines.sv, so it has to exist first.

Which results.txt numbers go into the Part 3 FoM, and which FoM input doesn't come from DC at all?

The slack line (must be MET at the period), the total power and the total cell area. The cycle counts come from simulation; DC never runs your design.

Why does this page keep saying "not DC"?

DC isn't available off caddy and nobody has run it on this design. The local numbers come from Yosys, an open-source synthesizer using the same Nangate cells. It shows the same kinds of effects, but with its own algorithms and numbers.

Why the order matters

  • Read, then constrain, then compile. The constraints name ports (clk, rst_n, instruction_count), so the design must exist first. Constraints set after compile_ultra would only change the reports, not the gates.
  • Every report comes after compile, so it describes the mapped Nangate netlist, not your RTL.
  • Each run starts from scratch (remove_design -all), but results.txt doesn't: it's appended to.
  • Nothing in the script reads your testbenches or the real memory model. Synthesis only sees logical/*.sv (minus logical/array.sv), defines.sv and the empty macros/array.sv.

Quiz yourself

The script sets a 1.5 ns input delay on all inputs except clk and rst_n. Why does that have no effect in this design?

top's only other input is instruction_count, and the next set_input_delay sets it back to 0. A later input delay on the same port and clock replaces the earlier one.

What does set_dont_touch_network rst_n buy you, and what does it cost?

DC won't buffer or resize the reset net that fans out to every flop's reset pin. That saves area and keeps DC from "fixing" a net a real flow would build as a tree later. The cost: the reset net isn't fixed for transition or fanout, and paths from rst_n aren't timed (it has no input delay).

Make says the run succeeded. Is compile.log clean?

Not necessarily. The recipe pipes DC into tee, so make sees tee's exit status. Grep the log for lines starting with Error, and check that it ends with DC's exit statistics.

You rerun synthesis at 1.8 ns without make clean. What does results.txt look like?

Two blocks: the old 2.000 run's lines, then the 1.8 run's, because every echo/grep appends with >>. The reports and compile.log are overwritten, so only results.txt mixes runs.

Where does DesignWare come in?

dw_foundation.sldb is the synthetic library: DesignWare's implementations of operators like + and *, in several architectures each. Elaborate turns your operators into synthetic operators; compile picks an implementation for each one based on timing and area.

1 · High-level optimization: deciding what to build

Resource sharing. If two operations can never be needed in the same cycle, one piece of hardware can do both, with muxes on its inputs. DC's high-level optimization looks for this DC docs. Yosys has a sharing pass too, and the result depends on its internals Yosys: written as sel ? a*b : a*c, Yosys's default flow built two 16 × 16 multipliers ({{Y:share_two_muls:area:0}} µm²). With one of its earlier passes skipped, its sharing pass merged them ({{Y:share_two_muls_noalumacc:area:0}} µm²). Written as a * (sel ? b : c), you get one multiplier by construction ({{Y:share_one_mul:area:0}} µm²). . This is the same idea as Part 3's "hardware reuse", where the question is how to share multipliers across modes.

Datapath extraction. DC Ultra can merge a cluster of arithmetic (say acc + a*b) into one carry-save adder tree with a single carry-propagate adder at the end, instead of a multiplier followed by a separate 64-bit adder DC docs. A multiplier is already "add up the partial products", so adding one more operand to its tree is nearly free. Yosys does the same with its $macc cell Yosys.

DesignWare architecture choice. For each operator DC picks an implementation from DesignWare (an adder can be a ripple chain or one of several parallel-prefix trees; a multiplier can be Booth-encoded or not) based on the timing constraint DC docs. Here is one 64-bit a + b built five ways in Yosys Yosys + open Nangate45, not DC. Dots are the plain mappings; arrows show what gate sizing did afterward:

The ripple-like adder is the smallest and about {{R:add64_area:add64_ks:delay:1}}× slower than Kogge-Stone; Kogge-Stone is about {{R:add64_ks:add64_area:area:1}}× the area. The "ripple-like" one came from Yosys's default flow, whose generic ABC pass restructures for area and turns the prefix tree back into a {{Y:add64_area:gates}}-gate chain. That's what a synthesizer does when nothing tells it to be fast. Give DC a tight clock and it does the opposite: it chooses the faster architecture. That's why the same RTL can be bigger at a shorter clock period.

2 · Logic optimization: structuring and flattening

DC rewrites the Boolean logic DC docs. Structuring factors out shared subexpressions into a multi-level network: smaller, more levels. Flattening collapses logic toward two-level sum-of-products: fewer levels, often bigger. compile_ultra decides per region based on timing. What it can't do is use facts you never told it. An if / else if chain over eight requests became a chain of {{Y:prio_chain:cells}} cells and {{Y:prio_chain:delay:0}} ps. The same selection written as an AND-OR, valid only when the requests are one-hot, took {{Y:onehot_andor:cells}} cells and {{Y:onehot_andor:delay:0}} ps Yosys. Lecture 05 p47 says it: tools are better than you at gates; you're better at the problem.

3 · Technology mapping: picking Nangate cells

The open .lib has {{L:cell_count}} cells .lib; the course's own Milkyway folder (synth/lib/NangateOpenCellLibrary/CEL/) lists the same ones except the TAPCELL_X1 tap cell: inverters and buffers in drive strengths X1 to X32, NAND/NOR/AND/OR with 2 to 4 inputs, AOI/OAI complex gates, XOR/XNOR, MUX2, full and half adders (FA_X1, HA_X1), flip-flops (DFF, with reset DFFR, with set DFFS, both DFFRS, scan SDFF), latches (DLH, DLL), clock-gating cells (CLKGATE, CLKGATETST), tie cells (LOGIC0, LOGIC1) and fillers. Every cell is 1.4 µm tall and a whole number of 0.19 µm sites wide (the technology file's unit tile), so area = 0.266 µm² × sites: an INV_X1 is 2 sites ({{L:cells|INV_X1|area:3}} µm²), a DFF_X1 17 sites ({{L:cells|DFF_X1|area:3}} µm²).

The mapper covers your logic with these cells to minimize delay on critical paths and area elsewhere. One concrete difference you'll see: DC can use FA_X1 (two outputs, S and CO); Yosys's mapper ABC can't use multi-output cells and says so in its log ("Detected 2 multi-output cells"), so its adders come out as XOR/AOI/OAI gates.

4 · Gate sizing and buffering: logical effort, automated

Lecture 05 p3: a gate's delay is Rgate × (load + parasitic C). A bigger gate has a smaller R but a bigger input capacitance, which loads the gate before it. Here are real Nangate inverters, read from the .lib's delay tables at a 20 ps input slope .lib:

INV_X4 drives a load about {{RL:drive|INV_X1|R_avg_kohm:drive|INV_X4|R_avg_kohm:1}}× faster than INV_X1 (effective drive resistance {{L:drive|INV_X4|R_avg_kohm:2}} kΩ, vs {{L:drive|INV_X1|R_avg_kohm:2}} kΩ for INV_X1), and it presents {{RL:drive|INV_X4|cin_fF:drive|INV_X1|cin_fF:1}}× the input capacitance ({{L:drive|INV_X4|cin_fF:2}} vs {{L:drive|INV_X1|cin_fF:2}} fF) and {{RL:cells|INV_X4|area:cells|INV_X1|area:1}}× the area. A fanout-of-4 inverter delay (FO4, lecture 05 p14) in this library is {{L:fo4_ps|avg:0}} ps, so 2 ns is about {{L:fo4_ps|per_2ns:0}} FO4: a relaxed clock by industry standards.

The same numbers give each gate's logical effort the way lecture 05 p28 defines it: the product of its resistance ratio and its capacitance ratio relative to an inverter. From the .lib, at this operating point:

Real cells aren't sized to match an inverter's drive, so "g from the .lib" folds in how Nangate sized each cell; NOR2 lands near the textbook value. The rise and fall resistances differ because the PMOS is weaker.

During compile DC does this sizing for every gate on a failing path: it upsizes drivers of heavy loads, inserts buffer trees for big fanouts, and picks cells by drive strength DC docs. ABC does the same kind of thing with buffer/upsize/dnsize Yosys: on the 64-bit Sklansky adder, whose prefix tree has nodes driving many loads, sizing and buffering cut the delay from {{Y:add64_sk:delay:0}} to {{Y:add64_sk_sized:delayN:0}} ps for {{Y:add64_sk_sized:area:0}} µm² instead of {{Y:add64_sk:area:0}}. On Brent-Kung, which has little fanout to fix, it bought less ({{Y:add64_bk:delay:0}} → {{Y:add64_bk_sized:delayN:0}} ps).

Design rules come first. DC also fixes design-rule violations: the library's default_max_transition ({{L:default_max_transition:3}} ns) and per-pin max_capacitance, and the script's max fanout of 4 on input ports. In DC's cost function, design rules outrank timing, and timing outranks area (set_max_area) DC docs.

5 · Retiming

Retiming moves flip-flops across combinational logic without changing what the circuit computes cycle by cycle at its boundaries DC docs. If one stage has 2.4 ns of logic and the next 0.6 ns, moving the register between them by 0.9 ns of logic gives two 1.5 ns stages. The clock period drops from 2.4 to 1.5 ns, and the latency in cycles doesn't change.

set_optimize_registers true -design top plus compile_ultra -retime lets DC do this anywhere. It's already in the script, even though the Part 3 handout (§2.2.2) tells you to add -retime.

What retiming needs from your RTL:

  • Registers to move. Retiming never adds pipeline stages; it only moves the ones you wrote. To split a long multiply into two cycles, the RTL has to have the extra register, and your controller has to expect the extra cycle of latency, keeping the valid signals high until the last WRITE commits.
  • Movable registers: the same clock, compatible reset and enable conditions, and not marked dont_touch. Registers whose reset values can't be recomputed after a move, or that are observed directly by something like a black-box pin, may be left in place DC docs.
  • Expect new names. Retimed flops get generated names, and their number can change. A testbench that peeks at an internal register by name only works on the RTL, which is fine because the course flow never simulates the netlist.

6 · Boundary optimization and auto-ungrouping

Boundary optimization pushes constants, unconnected pins and inverters across module boundaries DC docs. If top always ties a port of a sub-module to 0, the logic inside that depends on it can be simplified, and if an output is never used, the logic that drives it can go. Auto-ungrouping: compile_ultra dissolves small modules (or ones on critical paths) into their parent so it can optimize across the boundary. Two consequences for you:

  • Small modules, like a vector_decoder instance, may vanish from area_report_hier. That's expected.
  • Optimizing across boundaries is exactly what could remove logic whose only loads are the pins of an empty memory module. Whether DC does that with macros/array.sv is unverified. shows the risk and the check.

Quiz yourself

Why can the same RTL give a bigger area at a shorter clock period?

With more timing pressure DC picks faster DesignWare architectures (prefix adders instead of ripple), upsizes gates and adds buffers. The 64-bit adder above spans about 2× in area between its slow and fast versions.

What does logical effort have to do with synthesis?

Gate sizing is logical-effort optimization done automatically: DC trades a gate's drive (lower R) against its input capacitance (load on the previous stage) along critical paths, and inserts buffers for big fanouts (lecture 05 p3, p30). Lecture 05 p48 says this delay estimation is what synthesis uses to judge a gate implementation.

What does compile_ultra -retime need from your RTL?

Extra register stages to move (it never adds latency), on the same clock with compatible reset and enable and no dont_touch. Your controller must already account for the latency those stages add.

Will DC turn a priority if/else chain into an AND-OR for you?

Only if it can prove the conditions are mutually exclusive, and from your RTL it usually can't. If you know a signal is one-hot, write the logic that way (or use a case on it). Yosys's chain was about {{R:prio_chain:onehot_andor:delay:0}}× slower than the AND-OR.

What is datapath extraction, and why does it matter for a MAC?

DC merges connected arithmetic into one carry-save tree with a single final adder. For acc + a*b, the accumulator becomes one more row of the multiplier's partial-product tree, so you don't pay for a separate full-width adder after the multiplier.

Registers four ways

An async reset lives inside the flop (DFFR_X1). A sync reset or an enable is logic on the D input. In Part 2 your RTL style decides which cells you pay for, 96 times per PE.

Multipliers

  • Signed vs unsigned is an architecture question. In Yosys's plain array multiplier, signed 8 × 8 cost {{Y:mul8_signed:area:0}} µm² vs {{Y:mul8_unsigned:area:0}} unsigned: sign-extending the operands adds work. Booth encoding handles signed numbers natively ({{Y:mul8_signed_booth:area:0}} µm²). DC's DesignWare multipliers handle two's complement directly, so don't read Yosys's signed penalty as DC's.
  • Area grows about with the square of the width: Booth 8, 16, 32 bits: {{Y:mul8_signed_booth_keep:area:0}}, {{Y:mul16_signed_booth_keep:area:0}}, {{Y:mul32_signed_booth_keep:area:0}} µm² (structure kept). Double the width, about 4× the area.
  • A 32 × 32 multiply is a long path. ABC's estimate for the structure-kept versions is {{Y:mul32_signed_keep:delay:0}}–{{Y:mul32_signed_booth_keep:delay:0}} ps before any clock-to-Q, setup or wire load: close to the whole 2 ns cycle. DC's Booth-Wallace trees with fast final adders do better, but this is the path to watch, if it's timed at all ().

Quiz yourself

Why does an async-reset register cost more area than a plain one, but no extra gates?

The reset is built into the cell: DFFR_X1 ({{L:cells|DFFR_X1|area:2}} µm²) vs DFF_X1 ({{L:cells|DFF_X1|area:2}} µm²). A synchronous reset instead puts an AND gate in front of a plain flop, on the timed D path.

Why did the staff vector_decoder make Yosys stop, and what would DC do?

case (mode) has no arm for mode 3, so the outputs must hold their value there: a latch. Yosys treats a latch in always_comb as an error. DC is known to print warning ELAB-974 ("Netlist for always_comb block contains a latch") and build it: {{Y:vd_star:ncell.DLL_X1}} latch bits in Yosys's version.

In the empty-memory experiment, why did the black-box version also end up with 0 cells?

Synthesis keeps only logic that can affect an output or a kept cell. top has no outputs, and the MAC only feeds the memory's d, so nothing outside the loop needs it. Marking the instance keep brought back {{Y:bb_keep:cells}} cells.

Roughly how much of a 2 ns cycle do the flops themselves eat?

About {{SUMSEQ}} ps: DFF_X1 clock-to-Q (about {{L:seq|DFF_X1|CK->Q|cell_rise:0}} ps) plus setup (about {{L:seq|DFF_X1|setup|fall_constraint:0}} ps), more with heavy loads. Lecture 06 p13 calls this the sequencing overhead.

Why can't you trust Yosys's delay numbers as DC's?

Different mapping algorithms, no wire-load model, ideal input slopes, no flop overhead, and no DesignWare. They're right in kind (which structure is faster) and in rough size (hundreds of ps, not ns or ps), not in detail.

report_timing in one paragraph

    
A timing path starts at a launching register's clock pin (or an input port) and ends at a capturing register's D pin (or an output port). Arrival = the launch edge + clock-to-Q + every gate and wire on the way. Required = the capture edge − setup. Slack = required − arrival (lecture 06 p37–41). MET means slack ≥ 0. STA computes this for every path at once without simulating any data (lecture 06 p34), so it's conservative: it can flag a path that never actually happens (a false path, p44).

    
What's probably critical in this design

    
Think about which paths DC can actually see (). Data from the SRAMs' q pins has no timed startpoint, so if your PE multiplies the operands the cycle they leave the memory, the multiplier's partial products aren't timed. The timed candidates are:

    
    
      
  • The accumulator feedback: accumulator register → (the bottom of the multiply-accumulate tree) → the final carry-propagate adder → the mode/opcode mux → accumulator register. A carry across up to 64 bits is the classic critical path, and the sample above is one.
    • 
      
  • RND and OUT logic on the accumulator: a variable shift, a round-to-nearest-even increment, comparisons for clamping, then muxes.
    • 
      
  • The instruction fan-out: the controller's PE-instruction register drives every PE's decode, a fanout of thousands. DC must build buffer trees for it (lecture 05's fanout problem).
    • 
      
  • An operand-select path: a register that picks the MEM1 lane or the mode, driving the operand mux, then through the multiplier into the accumulator. It's timed even though the operand data isn't, as long as no latch sits in between. The Part 3 page's illustrative path is of this kind.
    • 
    

    
If your report's worst path is something else, don't panic. Read its startpoint and endpoint and ask why that path is long.

    
report_area in one paragraph

    
Combinational area is all gates, including buffers and inverters (buf/inv is a subset, not extra). Noncombinational is flops and latches. Macro/black box is 0 here because the memories are empty. Net interconnect is undefined because the wire-load table has no area. Total cell area is the FoM's area. The hierarchical report repeats this per instance; use it to check that every PE has real area.

    
report_power, and where its activity comes from

    
Dynamic power is P = ½ · α · C · V² · f per net (α = transitions per cycle, Review Session 2 p26; lecture 03 p48 writes the energy per gate as ½ α C VDD2). Add the cells' internal power and the leakage of every cell. Lecture 03 p50 puts the catch plainly: total power is just the sum over gates; "only problem is to estimate transition probabilities, and wire capacitance if you don't have physical design".

    
The course flow gives DC no simulation activity (no SAIF file), so DC uses defaults DC docs: by default a toggle rate of 0.1 per clock period and a static probability of 0.5 on primary inputs and on black-box outputs, propagated through the logic. It knows the clock toggles every cycle. Three consequences for Part 3:

    
    
      
  • Clock-related power is modeled well, data power only roughly. Every flop's clock pin switches every cycle in the model, as in reality, so the register group tends to dominate. Fewer flops, or clock gating, show up clearly in the report.
    • 
      
  • Real data activity is ignored. All operand bits come from SRAM black-box outputs, so they all get the same default activity, whatever your test data looks like. Tricks that only reduce data toggling (operand isolation, say) may barely move DC's number.
    • 
      
  • Leakage scales with area, so area savings pay twice in the FoM.
    • 
    

    
A -analysis_effort hi run propagates activity more carefully than the default, which is why compile.log's copy can differ slightly from power_report.

Quiz yourself

      
What is slack, and how do you read it off your timing report?
Required time − arrival time for the worst path. Required = capture edge (the clock period) − the capturing flop's setup; arrival = clock-to-Q + every gate and net. The last line, slack (MET) x or slack (VIOLATED) −x, gives it in ns.

      
Your slack is +0.35 ns at 2.0 ns. Can you claim 1.65 ns in Part 3?
Not without rerunning. At 1.65 ns DC re-optimizes (different architectures, sizes, retiming), so the new critical path and its slack are different. The rule is that synthesis at the claimed period must show no violation.

      
Why is "Buf/Inv area" not added to the total?
It's the part of the combinational area made of buffers and inverters, already included in combinational area.

      
Why don't you see the SRAMs in your area or power report?
Synthesis reads macros/array.sv, an empty module: no cells, so no area, no internal power and no leakage. Real SRAM macros would dominate both, which is why the FoM leaves memory out.

      
What sets dynamic power, and how does DC estimate activity here?
Switched capacitance, voltage squared, frequency and activity: P = ½ α C V² f per net, plus internal power. With no SAIF from simulation, DC applies default activity (0.1 toggles per cycle, probability 0.5) to inputs and black-box outputs and propagates it. The clock toggles every cycle, so flop clock pins dominate.

      
What does "slack (VIOLATED: increase significant digits)" mean?
The slack is negative but rounds to 0.00 at the printed precision. It's still a violation.

What that means

    

      
No area, no power
The arrays contribute 0 µm² and 0 mW. Area, leakage and power in your reports are logic and flops only. That's intended: the FoM compares logic.

      
Their pins aren't timed
An empty module has no timing arcs. Paths from a memory's q have no launching clock, and paths into its a, d, wen, cen, gwen have no setup check. standard STA, unverified here

      
top has no outputs
top's only ports are clk, rst_n and instruction_count. Every result your design computes ends at a memory's d pin. Those empty-module pins are the only thing that makes your logic "used".

      
Default activity at q
Black-box outputs get DC's default switching activity, so every operand bit looks equally busy to the power estimate, whatever the data. DC docs

Writing RTL that synthesizes the way you intend

    

      
always_ff for flops, always_comb for logic
Lecture 09 p23 recommends both. In always_ff use only <=; in always_comb only = (p24). Then a mistake shows up as a tool message instead of silent wrong hardware: a latch in always_comb is ELAB-974 in DC and an error in Yosys.

      
Assign every output on every path
Lecture 09 p21: in a combinational block, every variable must be assigned under all conditions, or you get a latch. Either give every case a default, or (simpler) start the block with default assignments:
always_comb begin
  nxt = cur;            // default: hold
  case (op)
    OP_A: nxt = a;
    OP_B: nxt = b;
  endcase
end

      
One driver per signal
A logic can't have two drivers (lecture 09 p26). Two always blocks writing the same variable is ELAB-366 in DC, even if you "know" they never write at the same time.

      
No initial, no #delays, no $display in logical/
Synthesis ignores initial blocks and delays and can't build file I/O, so the netlist would differ from your simulation. Reset your registers instead. logical/array.sv is full of initial and tasks; that's fine only because synthesis never reads it (it reads macros/array.sv).

      
Loop bounds must be constants
A for loop is unrolled at elaboration: for (i = 0; i < 4; i++) becomes four copies of the hardware. Bounds from parameters or `defines are fine; a bound from a signal is not hardware. Lecture 09 p34: "all genvars must disappear after static elaboration".

      
Avoid accidental priority
An if / else if chain builds a priority chain: one gate level per condition (). If the conditions are mutually exclusive, a case on one select signal says so. Use unique/priority only if you know what they promise the tool.

      
Mind signedness and widths
An expression is signed only if every operand is signed; one unsigned operand makes the whole expression unsigned and changes the hardware (an unsigned multiplier). Size intermediate results for their full width (a 32 × 32 product needs 64 bits).

      
Keep the port names
The script constrains ports named clk and rst_n, and the testbench reaches into fixed instance names (dut.u_buffer.u_matrix_mem ...). Don't rename them.

    


    
Simulation semantics vs synthesis semantics

    
A simulator executes your code as events in time; a synthesizer reads it as a description of hardware. They agree only for code written in the synthesizable style. The given memory model is a real example. logical/array.sv updates read_data with a blocking assignment in a clocked block and drives q from a separate latch-style block. That's a race against any flop that samples q on the same edge from the files:

    
    
      
  • Event-driven simulators (Icarus, and very likely VCS) run every posedge block before the latch block updates q, so consumers see the pre-edge value: a normal synchronous SRAM.
    • 
      
  • Verilator at default optimization inlines the instruction memory's array and makes q an alias of read_data, so a controller that latches inst at the edge gets the next instruction: it skips the first instruction of every program. -fno-inline fixes it checked locally. That's why this repo's flow uses Icarus by default for pass/fail and -O2 -fno-inline when SIM=verilator; make lint uses Verilator for lint only.
    • 
      
  • Synthesis never sees this race: it reads the empty macros/array.sv. The race lives only in simulation, and blocking assignments in clocked blocks are exactly the style that creates such races. Use <= in your always_ff blocks (lecture 09 p24 and the quiz on p28).
    • 
    

    
Quiz yourself

      
Why would a latch appear in your netlist?
A combinational block didn't assign some output on some path (an if without else, a case without default), so the hardware must remember the old value. DC reports it as ELAB-974 for an always_comb and lists it as "Latch" in the inferred-memory table.

      
The log has 300 warnings and no errors. Are you done for Part 2?
For the requirement, yes. But skim the warning IDs: ELAB-974 pointing at your own file, LINK-5, or timing-loop messages mean real bugs that the equivalence tests might not catch.

      
Why is it OK that logical/array.sv uses initial blocks and tasks?
Synthesis never reads it; the script reads macros/array.sv. The simulation model only has to simulate, and its loadmem/dumpmem tasks exist for the testbench.

      
Two always_ff blocks both write out_reg, in different opcodes. Why does DC refuse?
Each block describes its own set of flops driving the same net: multiple drivers (ELAB-366). Hardware has no "only one of them runs" rule. Put all the writes in one block.

Words this page uses

    

      
RTL (register-transfer level)
Hardware described as registers plus the logic between them, cycle by cycle. Your .sv files.

      
Logic synthesis
Turning RTL into a netlist of library cells that meets constraints. Here, DC with compile_ultra.

      
Netlist
A list of cell instances and the wires between them. netlist/top.mapped.v.

      
Standard cell
A pre-designed gate or flop of fixed height, with known area, delay and power. Nangate has about 135.

      
Liberty (.lib) / .db
The library description: cell functions, areas, pin capacitances, delay and power tables, design rules. .lib is text; .db is Synopsys's compiled form.

      
NLDM
Non-linear delay model: delay and output slope looked up in a table by input slope and output load.

      
GTECH
Synopsys's technology-independent generic gates, used between elaborate and compile.

      
DesignWare
Synopsys's library of operator implementations (adders, multipliers ...) in several architectures; dw_foundation.sldb.

      
Synthetic operator
An operator like + after elaboration, before DesignWare has picked an implementation.

      
analyze / elaborate / link
Parse the files / build the parameterized hierarchy into generic logic / resolve every instance to a design or cell.

      
Constraint
A goal or assumption for synthesis: the clock period, input delays, drive, wire loads, area goal.

      
Wire-load model
A table that guesses a net's capacitance and resistance from its fanout, before placement exists.

      
Fanout
How many gate inputs a net drives.

      
Drive strength (X1, X2, X4 ...)
Versions of one cell with lower output resistance, more input capacitance and more area.

      
FO4
The delay of an inverter driving four copies of itself: {{L:fo4_ps|avg:0}} ps in this library. A unit of gate delay.

      
Logical effort (g)
How much worse a gate is than an inverter at driving a load for the same input capacitance (lecture 05).

      
STA (static timing analysis)
Computing the worst arrival time at every point from the gate delays, without simulating any data.

      
Startpoint / endpoint
Where a timing path begins (a register clock pin or an input) and ends (a register data pin or an output).

      
Arrival / required time
When the data actually gets to a point / the latest it may get there.

      
Slack
Required − arrival. ≥ 0 is MET; negative is VIOLATED.

      
Setup / hold time
How long before / after the clock edge a flop's input must be stable.

      
Clock-to-Q (tpcq)
How long after the clock edge a flop's output changes.

      
Critical path
The path with the worst slack; it sets the minimum clock period.

      
Ideal clock
A clock with zero delay and skew, as in synthesis before a clock tree exists.

      
Path group
Timing paths grouped by capture clock; reports show the worst path per group.

      
WNS / TNS
Worst negative slack / total negative slack summed over failing endpoints.

      
Design rules (DRC)
Electrical limits from the library: max transition, max capacitance, max fanout. Fixed before timing.

      
Gate sizing / buffering
Swapping a cell for a stronger or weaker version / inserting buffers to split a big load.

      
Resource sharing
One hardware unit doing several operations that never happen in the same cycle, with muxes on its inputs.

      
Datapath extraction
Merging connected arithmetic into one carry-save tree with a single final adder.

      
Carry-save / prefix adder
An adder that defers carries (used inside multipliers) / a fast adder that computes all carries in log2(n) levels (Brent-Kung, Kogge-Stone ...).

      
Booth encoding
A way to recode one multiplier operand so there are about half as many partial products; handles two's complement naturally.

      
Retiming
Moving registers across logic to balance stage delays without changing behavior at the boundaries.

      
Boundary optimization
Optimizing across module boundaries (constants, unused pins, inversions).

      
Ungrouping
Dissolving a module instance into its parent so its logic can be optimized with the parent's.

      
Black box
A cell or module whose insides the tool doesn't know; here, the empty memory modules.

      
Macro
A large pre-built block like an SRAM, placed as one cell.

      
Latch
A level-sensitive storage element: transparent while enabled, holding otherwise. Inferred when combinational code forgets a case.

      
Dynamic / internal / switching / leakage power
Power from switching (internal power inside cells + switching power charging nets) / power drawn even when nothing switches.

      
Activity factor (α) / toggle rate
How often a net switches per clock cycle.

      
SAIF
A file of switching activity from simulation that a power tool can use instead of defaults; not used in this flow.

      
Clock gating
Stopping the clock to registers that don't need to change, so they don't burn clock power.

      
QoR
Quality of results: DC's summary report.

      
FoM
Part 3's figure of merit: (total test time)2.3 × area × power × 10−15.

    

    
Quiz yourself (mixed)

      
What is GTECH and when does your design exist in that form?
Synopsys's generic, technology-independent gates. Your design is GTECH plus synthetic operators between elaborate and compile_ultra; compile maps it to Nangate cells.

      
What does a wire-load model approximate, and is the course's optimistic or pessimistic?
The capacitance and resistance of each net before placement, from its fanout. 1K_hvratio_1_4 gives a fanout-4 net only {{WLM4C}} fF, less than one gate input, so it's likely optimistic for a block this size.

      
Why does DC report a 2 ns clock as "relaxed"? Put a number on it.
2 ns is about {{L:fo4_ps|per_2ns:0}} FO4 delays in this library (FO4 ≈ {{L:fo4_ps|avg:0}} ps). Aggressive processor pipelines run near 10–20 FO4 per cycle (lecture 06 p28 notes it's hard to go below 10–12 logic stages).
