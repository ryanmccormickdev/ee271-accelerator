# From the Python model to RTL (Part 2)

### What changes fundamentally when the Python simulator becomes RTL?
- **Tags:** part2, general, timing
- **Level:** core
- **Answer:** Time becomes explicit: a Python repetition was one loop iteration, in hardware it is pinned to clock cycles. State lives in flip-flops that only change at a rising edge, so everything I compute in a cycle is a register's next value. The SRAMs answer one cycle after the address, so a READ and the MAC that uses its data can't be in the same cycle. The PEs are `PE_COUNT` physical copies working at once, and the program arrives through a handshake with the instruction memory instead of a Python list.
- **See:** docs/part2-rtl.html#big-picture/bp-change

### Which files did you write, which were given, and which one is generated?
- **Tags:** part2, general
- **Level:** core
- **Answer:** We wrote `processing_element.sv`, `buffer.sv`, `controller.sv` and `top.sv` (the "Your Code Here" skeletons). `instruction_memory.sv` (program SRAM, program counter, prefetch) and `array.sv` (the SRAM model) are given. `defines.sv` is generated by `ivd-gv` on every build: widths, opcodes, the three packed structs, and the `vector_decoder` module.
- **See:** docs/part2-rtl.html#big-picture/bp-files

### How does the testbench load the matrices and read the results, and what does that require of your design?
- **Tags:** part2, verification, top
- **Level:** core
- **Answer:** Through hierarchical names: it calls `loadmem` on `dut.u_buffer.u_matrix_mem`, `dut.u_buffer.u_vector_mem` and `dut.u_instruction_memory.u_instruction_memory` at time 0, and `dumpmem` on `dut.u_buffer.u_output_mem` at the end. Its end condition reads `dut.u_instruction_memory.program_counter`, `dut.pe_inst_valid` and `dut.buf_inst_valid`. So the buffer instance must be `u_buffer`, the array names must stay, and `top` must have signals named exactly `pe_inst_valid` and `buf_inst_valid`, or the testbench doesn't even compile.
- **See:** docs/part2-rtl.html#big-picture/bp-names

### Python's _handle_read computes offset // 4 and offset % 4. What does that cost in hardware?
- **Tags:** part2, buffer, hardware
- **Level:** deeper
- **Answer:** Nothing: division and modulo by a power of two are bit selections. In INT8 the MEM1 word address is `memb_offset[15:2]` and the lane is `memb_offset[1:0]` (INT16: `[14:1]` and `[0]`; INT32: `[13:0]`). Those are wires into the SRAM address and the select of a multiplexer, inside the given `vector_decoder`.
- **See:** docs/part2-rtl.html#buffer/mb-read

### Walk me through, cycle by cycle, NOP|CLR followed by READ|MAC with count 3.
- **Tags:** part2, timing, controller
- **Level:** core
- **Answer:** In the reference timing: cycle 5, reset is released and the controller takes the CLR (`inst_exec_begins` = 1). Cycle 6, the buffer gets the CLR's NOP; it's the last repetition, so the controller takes READ|MAC in the same cycle. Cycles 7, 8, 9: `buf_inst` is READ 0 0, READ 1 1, READ 2 2, while `pe_inst` is CLR, MAC, MAC. Cycle 10: the buffer gets the next instruction's NOP and the PEs do the third MAC with READ 2 2's data. Every PE operation is one cycle behind its memory half.
- **Our design:** Does our controller produce exactly this, or a different (still valid) schedule? Which cycle is our first MAC in?
- **See:** docs/part2-rtl.html#controller

### Why does your PE instruction lag the buffer instruction by one cycle?
- **Tags:** part2, timing, controller, pe
- **Level:** core
- **Answer:** Because the SRAMs have one cycle of read latency. The buffer must see the READ in cycle t so the address is sampled at the end of t; the data is on `matrix_data` and `vector_data` only in t + 1, so the MAC has to happen then. We pass the PE half through one extra register, so each repetition's two halves stay paired. Every PE instruction is delayed, not just MAC.
- **Our design:** Where does our one-cycle delay live: in the controller, the buffer or the PE?
- **See:** docs/part2-rtl.html#cycles/cy-pe

### What would break if the PE instruction were not delayed, and would the official tests catch it?
- **Tags:** part2, timing, verification
- **Level:** deeper
- **Answer:** Every MAC would use the previous repetition's data: the first MAC of a tile uses stale data (zeros at the start, the previous tile's last column later), and the last column is never added. We measured that copy of the design: int8_test and int32_test fail with 16 of 16 rows wrong, but int16_test passes under Verilator, because the INT16 vector ends in 0, so the lost and the stale products are both zero. Under Icarus it fails on row 0, which comes out as X, because the first MAC reads the SRAM before anything was read.
- **See:** docs/part2-rtl.html#cycles/cy-bugs

### Why does your WRITE commit one cycle after it is issued?
- **Tags:** part2, timing, buffer
- **Level:** core
- **Answer:** Each tile ends with `NOP | OUT` then `WRITE | NOP`. With the PE half delayed, the OUT runs on the PEs in the same cycle the WRITE is on `buf_inst`, and the output registers only change at the end of that cycle. If the WRITE stored `output_data` in its own cycle, it would store the outputs from before the OUT. So the buffer remembers the WRITE and its address for one cycle and pulls `gwen` low in the next, when `output_data` holds the new results (cycle 12 for the first tile in the worked example).
- **Our design:** In which cycle does our WRITE commit, and which register remembers it?
- **See:** docs/part2-rtl.html#cycles/cy-write

### What would happen if the WRITE committed in its own cycle?
- **Tags:** part2, timing, verification
- **Level:** deeper
- **Answer:** MEM2 would get the output registers' old contents, which are zeros because the CLR at the start of each tile clears them. We recorded this bug: every MEM2 row comes out as 0, and all three official tests fail, 16 of 16 rows. The symptom "every row is zero" points straight at the WRITE timing, or at `gwen` never going low.
- **See:** docs/part2-rtl.html#cycles/write_not_delayed

### How does the instruction memory let you start a new instruction every cycle?
- **Tags:** part2, controller, timing
- **Level:** core
- **Answer:** It prefetches. `inst` always shows `imem[program_counter]`, and in a cycle where `advance_pointer` (our `inst_exec_begins`) is 1, it already presents `program_counter + 1` to its SRAM. So at the same edge the counter increments and the next word is fetched, and the next cycle's `inst` is already the next instruction. One cycle of `inst_exec_begins` advances by exactly one instruction.
- **See:** docs/part2-rtl.html#cycles/cy-fetch

### When exactly do you raise inst_exec_begins, and what goes wrong if it's high for two cycles in a row by mistake?
- **Tags:** part2, controller, handshake
- **Level:** core
- **Answer:** Only in cycles where the controller takes the instruction on `inst`: when `inst_valid` is 1 and it's IDLE or on its last repetition. Each high cycle moves `program_counter` on by one, so a stray second cycle skips an instruction the controller never looked at; never raising it stalls the program on one instruction. It's naturally a combinational function of the state, the repetition counter and `inst_valid`.
- **Our design:** What is our exact expression for `inst_exec_begins`?
- **See:** docs/part2-rtl.html#controller/ctl-hs

### The testbench prints a cycle count. What does it count, and why is the worked example 20?
- **Tags:** part2, timing, verification
- **Level:** core
- **Answer:** It prints `$time / 10` when it dumps MEM2, one clock period after `simulation_complete` rose, so it includes the 5 reset cycles. For the 6 × 3 INT16 example on 2 PEs: 5 reset cycles, 1 cycle to take the first instruction, 13 repetitions one per cycle (2 tiles × (CLR + 3 READ|MAC + OUT + WRITE) + 1 padding), and 1 cycle for the last PE instruction to drain: 20.

### Give the cycle formula for your design and check it on an official test.
- **Tags:** part2, timing, part3
- **Level:** deeper
- **Answer:** With zero bubbles, cycles = tiles × (columns + 3) + 8, where tiles = ceil(rows / (PEs × lanes)). int8_test with 16 PEs: 1024 / 64 = 16 tiles, so 16 × 1,027 + 8 = 16,440, which is what the reference design measured; int16 gives 8,248 and int32 4,152. The formula also matched 8, 32 and 64 PEs on INT32 (8,296 / 2,080 / 1,044) and 5 PEs on INT8 (53,412).
- **Our design:** What do our three runs print, and does our formula match?
- **See:** docs/part2-rtl.html#cycles/cy-count

### Why do bubbles matter so much for Part 3?
- **Tags:** part3, timing, fom
- **Level:** stretch
- **Answer:** The figure of merit is (T_int8 + T_int16 + T_int32)^2.3 × area × power, so total time enters with an exponent of 2.3. One bubble per instruction adds 64 cycles to each official test (measured: 16,504 / 8,312 / 4,216), which is about 1.5% worse FoM at the same clock; one bubble per repetition would nearly double the time, about 4.9× the FoM. That's why the controller takes the next instruction on the last repetition of the current one.
- **See:** docs/part2-rtl.html#cycles/cy-b2b

### How does the testbench know the run is over, and what would a deeper pipeline have to do?
- **Tags:** part2, verification, part3
- **Level:** core
- **Answer:** `simulation_complete = (program_counter == instruction_count) && !pe_inst_valid && !buf_inst_valid`. When it rises, the testbench waits one clock period and dumps MEM2. So the last WRITE must be in MEM2 by then. A deeper pipeline that commits writes later must keep a valid signal high until its last write has committed, or the dump happens too early.
- **See:** docs/part2-rtl.html#cycles/cy-end

### What is the padding instruction, and does it cause problems?
- **Tags:** part2, verification
- **Level:** deeper
- **Answer:** The Makefile passes INST_COUNT = lines + 1, and `ivd-as` pads the instruction file with all-zero words, so the RTL executes one extra all-zero instruction: `READ INT8 0 0 | MAC INT8` with one repetition. It runs after the last WRITE, so it only changes the accumulators, never MEM2. It costs one cycle. `ivd-sim` stops at the first all-zero word, so the Python never runs it.
- **See:** docs/part2-rtl.html#cycles/cy-end

### Could the testbench's end detector fire too early?
- **Tags:** part2, verification, part3
- **Level:** stretch
- **Answer:** Yes: it waits on `@(posedge simulation_complete)`, a combinational signal. If, while `program_counter == instruction_count`, one valid falls at the same edge another rises, an event-driven simulator can see a zero-width pulse and start the dump one cycle early. A controller with a bubble per instruction does this: Icarus reports 16,503 cycles on int8 and Verilator 16,504 (MEM2 was still right). In Part 3, make sure no such edge happens before the last write is in MEM2.
- **See:** docs/part2-rtl.html#verify/vd-race

### How does your PE handle the three modes?
- **Tags:** part2, pe, arithmetic
- **Level:** core
- **Answer:** Lanes are bit slices: lane k of a w-bit layout is `x[k*w +: w]`, and the accumulator lane is twice as wide (`acc[2*w*k +: 2*w]`). For MAC there's a signed multiplier and adder per lane: four 8 × 8, two 16 × 16 or one 32 × 32, and the mode selects which set of results becomes the next accumulator. Each lane's adder drops its own carry, so nothing crosses a lane boundary, and that's the "wrap" the spec asks for.
- **Our design:** Do we build all three sets of multipliers (7 in total) and select, or share them? (Part 3 suggests at most 4.)
- **See:** docs/part2-rtl.html#pe/pe-ops

### Why does acc[15:0] + $signed(a) * $signed(b) give the wrong answer?
- **Tags:** part2, pe, systemverilog
- **Level:** core
- **Answer:** A part-select like `acc[15:0]` is unsigned, and one unsigned operand makes the whole expression unsigned. Then every operand is zero-extended to the 16-bit context, including the ones wrapped in `$signed`. With acc = 10, a = −2 (0xFE), b = 3, the simulator computes 10 + 254 × 3 = 772 instead of 4 (checked in Icarus and Verilator). Every operand must be signed, for example by assigning the slices to `logic signed` signals first.
- **See:** docs/part2-rtl.html#pe/pe-signed

### What are the SystemVerilog rules for the width and signedness of an expression?
- **Tags:** part2, systemverilog
- **Level:** deeper
- **Answer:** The operands of arithmetic and comparison operators are context-determined: they're extended to the widest of all operands and the left-hand side, then the operation is done at that width. The expression is signed only if every operand is signed, and extension is sign-extension only for signed expressions. Concatenations are self-determined and unsigned, so `{a + b}` stays at the operand width and loses the carry. And `>>>` is arithmetic only on a signed operand.
- **See:** docs/part2-rtl.html#pe/pe-signed

### How does OUT decide whether to clamp, in hardware?
- **Tags:** part2, pe, arithmetic
- **Level:** core
- **Answer:** Per lane, two signed comparisons against −2^(w−1) and 2^(w−1) − 1 and a three-way select: the lower limit, the upper limit, or the low w bits. An equivalent check without comparators: a lane fits in w bits exactly when every bit above bit w − 1 is a copy of bit w − 1; if not, the sign bit says which limit to use. OUT doesn't change the accumulator. The INT8 test clamps 801 of its 1,024 outputs; INT16 and INT32 never clamp.
- **Our design:** Did we use comparators or the sign-bit check?
- **See:** docs/part2-rtl.html#pe/pe-ops

### Explain how RND rounds to nearest with ties to even, in bits.
- **Tags:** part2, pe, arithmetic
- **Level:** deeper
- **Answer:** q = x >>> s, an arithmetic shift, so q is floor(x / 2^s) and the shifted-out bits are the remainder r, which is always 0 to 2^s − 1. The guard bit is bit s − 1 (r ≥ half), the sticky bit is the OR of bits s − 2 to 0 (anything below half), and the lsb of q says whether q is odd. Round up exactly when guard AND (sticky OR lsb). Example: −3 with s = 1 gives q = −2, guard 1, sticky 0, lsb 0, so it stays −2 (−1.5 rounds to even).
- **See:** docs/part2-rtl.html#pe/pe-rnd

### What happens in RND when s is larger than the lane width?
- **Tags:** part2, pe, arithmetic
- **Level:** stretch
- **Answer:** The bits above the lane are copies of the sign bit, so q is 0 for a non-negative lane and −1 for a negative one, and the guard bit is the sign bit. For a negative lane the remainder is then more than half or exactly half, so it rounds up to 0 (for example −1 with s = 20 gives 0, as −1/2^20 should); a non-negative lane gives 0. The hardware needs the shifter and the sticky mask to handle s up to 31 on a 16-bit lane.
- **See:** docs/part2-rtl.html#pe/pe-rnd

### Why does the PE need pe_inst_valid?
- **Tags:** part2, pe, controller
- **Level:** core
- **Answer:** `pe_inst` holds whatever bits the controller's registers hold when nothing is running: during reset and after the program it reads as `MAC INT8` (all zeros). With the valid at 0 the PE must hold both registers whatever the bits say. Without it the PE would keep MACing garbage, for example during the cycles between the end of the program and the dump.
- **See:** docs/part2-rtl.html#pe/pe-ops

### How are your registers written, and why that style?
- **Tags:** part2, pe, systemverilog
- **Level:** core
- **Answer:** Next values in an `always_comb` block that first assigns "hold" (so nothing is left unassigned and no latch is inferred), then a small `always_ff @(posedge clk, negedge rst_n)` that resets to 0 when `rst_n` is low and otherwise loads the next value with `<=`. The asynchronous active-low reset matches the given instruction memory. Non-blocking assignments make all registers update together, like real flip-flops.
- **Our design:** Point to the always_comb and always_ff blocks in our PE.
- **See:** docs/part2-rtl.html#pe/pe-pattern

### Describe the SRAM model's ports and read timing.
- **Tags:** part2, buffer, memory
- **Level:** core
- **Answer:** All controls are active low: `cen` enables the chip, `gwen` enables writing, and `wen` is a per-bit write mask. At a rising edge with `cen` = 0, `read_data` becomes `data[a]` and `q` follows it while `cen` stays 0, so the word for an address presented in cycle t is on `q` in cycle t + 1. A write happens at the edge when `cen` and `gwen` are both 0, for the bits where `wen` is 0. In synthesis the model is an empty black box, so it adds no area and isn't timed.
- **See:** docs/part2-rtl.html#buffer/mb-array

### Why does vector_decoder have two address inputs but only one mode input, and how did you handle it?
- **Tags:** part2, buffer, timing
- **Level:** deeper
- **Answer:** The word address is needed in the READ's own cycle (from the live offset), but the lane select is needed one cycle later, when the word comes back (from an offset kept in a register): hence `addr_from_controller` and `addr_from_controller_reg`. The mode is needed in both cycles but there's only one input, and in the data cycle the controller may already show another instruction. The reference uses two decoder instances: one with the live offset and mode for the address, one with the registered offset and mode for the data.
- **Our design:** How many decoders do we use, and where do we keep the READ's offset and mode?
- **See:** docs/part2-rtl.html#buffer/mb-dec

### If the MEM1 data were decoded with the current cycle's mode, why would all three official tests still pass?
- **Tags:** part2, buffer, verification
- **Level:** stretch
- **Answer:** It only matters in the cycle after the last READ of a run, when the controller already shows the OUT's NOP, whose mode field is 0 (INT8) because the assembler only sets the mode for READ. So the last column's vector element gets decoded as a byte. The INT16 test's vector ends in 0, and the INT32 test's ends in −1 = 0xFFFFFFFF, whose bytes are all identical, so the wrong decode gives the right value. With vector seed 7 the same design fails INT16 and INT32 on 16 of 16 rows; INT8 is unaffected because its mode is 0 anyway.
- **See:** docs/part2-rtl.html#cycles/live_mode

### Why is MEM2 instantiated with INITIALIZE_MEMORY(1)?
- **Tags:** part2, buffer, verification
- **Level:** core
- **Answer:** The testbench dumps all 65,536 MEM2 words and diffs them line by line with `ivd-sim`'s output, where every word the program never writes is 0. With the zero fill, unwritten RTL words are 0 too; without it they'd be X in a 4-state simulator and the diff would fail. It's a simulation feature only: the black-box SRAM in synthesis has no initial value.
- **See:** docs/part2-rtl.html#code/cmf-part2-unoptimized-verilog-logical-array-sv

### Describe your controller's state machine.
- **Tags:** part2, controller
- **Level:** core
- **Answer:** Two states from the given enum: IDLE takes `inst` as soon as `inst_valid` is 1; EXECUTING sends one repetition per cycle. On the last repetition, if another instruction is valid, it's taken in that same cycle and the state stays EXECUTING; otherwise it goes back to IDLE. In the worked example the controller is IDLE only in cycle 5 and from cycle 19.

### How does "Count + 1 repetitions" become hardware?
- **Tags:** part2, controller
- **Level:** core
- **Answer:** The assembler stores the written count minus one, so the hardware runs `count + 1` repetitions. A down-counter loaded with `count` when the instruction is taken makes "last repetition" simply "counter == 0". CLR, OUT and WRITE have count 0, so they're on their last repetition in their first cycle and take exactly one cycle.
- **Our design:** Up-counter or down-counter? What's its width, and where is it compared?
- **See:** docs/part2-rtl.html#controller/ctl-count

### How do the offsets advance, and when are they reloaded?
- **Tags:** part2, controller
- **Level:** deeper
- **Answer:** Two offset registers are loaded with the instruction's `mema_offset` and `memb_offset` when it's taken, and `mema_inc` / `memb_inc` (1 bit each) are added after every repetition. `buf_inst` carries the instruction's opcode and mode with the offsets from these registers. In the run: READ 0 0, 1 1, 2 2 for tile 0, then the next instruction reloads them, and tile 1 goes READ 3 0, 4 1, 5 2.
- **See:** docs/part2-rtl.html#controller/ctl-off

### How do you build the PE array, and how does each PE get its data?

### Why must the slice order be the same for matrix_data and output_data?
- **Tags:** part2, top
- **Level:** deeper
- **Answer:** The compiler packs a tile's rows into each MEM0 word left to right, and `extract_results_from_memory` reads MEM2 left to right. So the PE that reads the leftmost slice must write the leftmost slice. We measured a copy that reverses only the outputs: the numbers are right but in the wrong places ([7 6 −3 12] instead of [−3 12 7 6]), and all 16 rows of every official test fail.
- **See:** docs/part2-rtl.html#top/tp-order

### Why might Verilator and VCS disagree on your design?
- **Tags:** part2, verification, simulation
- **Level:** deeper
- **Answer:** Verilator is 2-state: X and Z become 0, so a design that reads an uninitialized value can pass there and fail in a 4-state simulator such as VCS or Icarus. And with default flags Verilator inlines the given instruction memory and turns its SRAM output into an alias of a blocking-assigned variable, so a controller flop that loads `inst` directly sees the next instruction at the same edge: the first instruction is skipped. With `-fno-inline` it matches Icarus on every signal, which is why our local flow uses Icarus for pass/fail and builds Verilator with `-fno-inline`.
- **See:** docs/part2-rtl.html#verify/vd-race

### A MEM2 diff shows line 3 differs. How do you find the bug?
- **Tags:** part2, verification, debugging
- **Level:** core
- **Answer:** Line 3 is MEM2[2], the third row tile. With 16 PEs in INT16 a tile is 32 rows, so rows 64 to 95; each 32-bit slice is one PE, and lane k of PE i is row 64 + 2i + (1 − k). Then the pattern tells you where to look: all lanes wrong by small amounts suggests one column's products (vector decode or MAC pairing), everything zero suggests the WRITE timing, the right numbers in the wrong slices suggest PE order. Then open the waveform at that tile's cycles.
- **See:** docs/part2-rtl.html#verify/vd-mismatch

### Name three SystemVerilog traps you hit or avoided.
- **Tags:** part2, systemverilog
- **Level:** core
- **Answer:** An `always_comb` with an incomplete `if` or `case` describes a latch; Verilator's lint and Yosys both flag it, and the given `vector_decoder` has one for mode 3. Blocking assignments in `always_ff` make later lines see new values, so a two-stage delay collapses into one. A register without reset is X in VCS and Icarus but 0 in Verilator. Also: one unsigned operand makes a whole expression unsigned, `x[8*k+7:8*k]` with a variable k is illegal (use `x[8*k +: 8]`), and a comment whose first word is "verilator" is a pragma error in Verilator.
- **Our design:** Which of these did we actually run into?
- **See:** docs/part2-rtl.html#primer/pr-traps
