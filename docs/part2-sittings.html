1 The picture and the one timing rule

10 minread only

What the machine does. The controller reads one instruction at a time from the instruction memory and repeats it count + 1 times, one repetition per clock cycle. Every repetition has two halves: a memory half (buf_inst, sent to the buffer: READ / WRITE / NOP) and a compute half (pe_inst, sent to all 16 PEs: MAC / OUT / CLR / …). That's the same READ | MAC pairing you had in Part 1.

The buffer is three memories. MEM0 holds the matrix: one 512-bit word gives each of the 16 PEs 32 bits. MEM1 holds the vector, in 32-bit words. MEM2 receives the results, in 512-bit words. All three are instances of the staff's array module, already placed in buffer.sv; you wire them up.

The one rule everything else follows from: the memories are synchronous. You give an address in cycle t; the data comes out in cycle t+1. Writing it out:

cycle tcycle t+1
READbuffer sends the addresses to MEM0/MEM1the data is on matrix_data / vector_data
PE op of that repetition(not yet: no data)runs on that data; its result is stored at the end of t+1
WRITEbuffer notes "write pending"MEM2 stores output_data (which by now includes the OUT just before)

So: the controller sends buf_inst first and the matching pe_inst one cycle later, and the buffer has to remember a few things from cycle t to use in t+1. Every one of those is a register you'll write.

Your files: buffer.sv (wire the memories, remember what's needed for one cycle), controller.sv (count repetitions, step addresses, delay the PE half), top.sv (plug it all together, no logic). Your partner writes processing_element.sv.

Done when you can say it out loud: "address in t, data in t+1, so the PE works one cycle after its READ, and a WRITE lands one cycle after it's issued." Deeper (laptop): the animated Cycles tab.

▶ Watch it run: the whole chip, cycle by cycle

optional5–15 minno terminal

This is a real run of a working design through the staff testbench, recorded one value per signal per cycle. It multiplies a 6×3 INT16 matrix by a 3-element vector on 2 PEs (yours has 16; nothing else changes) and takes 21 cycles from reset to "done". Step through it and watch the program, the controller, the three memories and the PEs.

How to read it: every value is what the signal holds during that cycle. Registers change only at the clock edge that ends a cycle; an orange → 9 shows what a register becomes at that edge. ← and → step once you've clicked inside the simulator. Heads-up: this shows a complete, working timing, including the controller columns Sitting 9 asks you to predict.

What's being computed

y = M · v with the 6×3 matrix below and v = [2, −1, 3]. The compiler splits M into tiles of 4 rows (2 PEs × 2 INT16 lanes each). Each MEM0 word holds one column of one tile, first row in the most significant bits, so tile 1 is words 0–2 and tile 2 is words 3–5. Tile 2 has only 2 real rows; rows 6 and 7 are zero padding. MEM1 packs two vector elements per 32-bit word. Each tile's program is CLR, three READ | MAC repetitions (one per column), OUT, then WRITE to the next MEM2 word.

Expected result: y = [−3, 12, 7, 6, 8, −6]. The testbench dumps MEM2 at the end and compares it with the Python model; this run matches. Source: docs/part2-rtl-src/waves.json, design ref, embedded by scripts/sittings_sim_data.py.

2 Four building blocks of SystemVerilog

10 minread only

You're not writing steps for a processor. You're describing wires and registers that all exist at once and all update on the same clock. This project needs only four building blocks. Here they are in a made-up example (a counter), not project code:

// 1. Signals: give every signal a width.
logic [15:0] count;      // 16 bits, bit 15 on the left
logic        busy;       // 1 bit

// 2. A wire with an equation: busy is ALWAYS equal to this. No order, no "running".
assign busy = (count != '0);           // '0 means "all zeros", any width

// 3. A register: changes only at the rising clock edge (or right away on reset).
always_ff @(posedge clk, negedge rst_n) begin
    if (!rst_n) begin                  // reset is active-low: rst_n == 0 means "reset now"
        count <= '0;                   // every register gets a reset value
    end else if (busy) begin
        count <= count - 1'b1;         // <= inside always_ff, always
    end
end

// 4. An instance: one physical copy of another module, ports connected BY NAME.
timer u_timer (                        // module name, then your name for this copy
    .clk(clk),                         // .port_name(my_signal)
    .start(busy),
    .done()                            // empty () = not connected
);

Two rules that prevent most beginner bugs: (1) registers live in always_ff and use <=; everything combinational is an assign. (2) Every register gets a value in the reset branch. (A register without one is x, unknown, and x spreads.)

The names you'll use (from the generated defines.sv)

A struct is a bundle of fields; read a field with a dot: buf_inst.mema_offset. Backtick names like `BUF_WRITE are constants.

TypeFields (widths)
buf_inst_topcode (2) · mode (2) · mema_offset (16) · memb_offset (16)
pe_inst_topcode (2) · mode (2) · value (5)
instruction_tbuf_instruction (a buf_inst_t) · pe_instruction (a pe_inst_t) · count (16) · mema_inc (1) · memb_inc (1)

Buffer opcodes: `BUF_READ = 0, `BUF_WRITE = 1, `BUF_NOP = 2. Widths: `BUF_MEMB_OFFSET_BITWIDTH = 16, `BUF_MODE_BITWIDTH = 2, `MEM1_ADDR_WIDTH = 14, `MEM1_BITWIDTH = 32, `MEM2_ADDR_WIDTH = 16, `MEM0_BITWIDTH = `MEM2_BITWIDTH = 512, `CONTROLLER_COUNT_BITWIDTH = 16, `PE_COUNT = 16. Operators: ==, !=, && (and), || (or), !x / ~x (not).

Done when you can say why count needs a reset and busy doesn't. Deeper (laptop): SystemVerilog for Python programmers.

6 Buffer 3/4: the vector path

laptop20–25 minthe trickiest buffer sitting

Why. defines.sv gives you a module, vector_decoder, that does both MEM1 jobs: it turns an offset into a MEM1 word address, and it picks the right lane out of the word that comes back and copies it to all lanes for the PEs. 7 Buffer 4/4: the write path

laptop20 min

Why. Every program ends a tile with NOP | OUT followed by WRITE | NOP. The OUT updates the PE outputs at the end of the cycle the WRITE is issued in. If MEM2 stored output_data during the WRITE's own cycle, it would store the old values (zeros). So the buffer waits one cycle: it remembers "a write is pending" and its address, then writes. MEM2's write enable is active-low. The skeleton already connects it to write_control_n; you drive that signal.

Do
  1. Declare a 1-bit register (the pending flag) and a `MEM2_ADDR_WIDTH-bit register (the address).
  2. One always_ff: on reset both get 0. Otherwise, every cycle: pending ← "this cycle has a valid WRITE", meaning buf_inst_valid and buf_inst.opcode == `BUF_WRITE; address ← buf_inst.mema_offset.
  3. Drive write_control_n with the opposite of pending (active-low).
  4. In u_output_mem: .a() ← your address register, .d() ← output_data.

9 The controller on paper

15 minpen and paper

Why. Ten minutes predicting the schedule saves an hour of guessing at the keyboard. The rules:

  • The controller takes an instruction (raises inst_exec_begins for that one cycle) when one is valid and it's either idle or on the last repetition of the current one. That's why there are no gaps.
  • The first repetition's buf_inst goes out the cycle after the take.
  • Each pe_inst goes out one cycle after its buf_inst (the memory rule from Sitting 1).
  • The count in a .asm line is the number of repetitions. (The assembler stores it minus one, which is why the hardware runs count + 1.)

Program (the check's basic.asm). After it comes one all-zero padding word, which means READ INT8 0 0 | MAC INT8, 1 repetition:

NOP           | CLR INT8 | 1 0 0      // count  MemA-inc  MemB-inc
READ INT8 0 0 | MAC INT8 | 4 1 1
NOP           | OUT INT8 | 1 0 0
WRITE 0       | NOP INT8 | 1 0 0
(padding: READ INT8 0 0 | MAC INT8 | 1 0 0)

On paper, make columns cycle 0–10 · buf_inst · pe_inst · inst_exec_begins. Cycle 0 is the first cycle after reset, when the CLR is already valid. Fill it in, then reveal.

10 Controller 1/4: issue each instruction

laptop25 minthe biggest sitting

Why. The controller is a two-state machine (the skeleton declares state: IDLE, EXECUTING) plus a down-counter. Build the basic version first: offsets don't step yet, and there's a gap between instructions. The next three sittings fix those, one at a time.

PieceKindWhat it does

remainingregister, `CONTROLLER_COUNT_BITWIDTHrepetitions left after this one: loaded with inst.count, counts down

Do
  1. Declare cur, remaining, last_rep, take.
  2. assign last_rep, take and inst_exec_begins.
  3. One always_ff, in this order (the order matters in Sitting 13): reset → state IDLE, cur and remaining 0. Else if take → EXECUTING, cur ← inst, remaining ← inst.count. Else if EXECUTING → if last_rep, go to IDLE; otherwise remaining ← remaining − 1.
  4. Outputs, all assign: buf_inst_valid = (state is EXECUTING). The four fields of buf_inst come from cur.buf_instruction, offsets too for now. pe_inst = cur.pe_instruction; pe_inst_valid = (state is EXECUTING).

endgenerate
// x[8*i +: 8] means "8 bits starting at bit 8*i, going up"

The order matters: the PE that reads the leftmost 32 bits of matrix_data must write the leftmost 32 bits of output_data.
