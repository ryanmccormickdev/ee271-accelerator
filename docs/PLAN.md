## The design: what exists and what we write

```
top ── instruction_memory (given)  ── array (given SRAM model; synthesis uses an empty black box)
    ├─ controller          (ours)   FSM: fetch an instruction, issue its Count+1 repetitions
    ├─ buffer              (ours)   MEM0/MEM1/MEM2 (three `array`s) + the generated vector_decoder
    └─ processing_element  (ours) x PE_COUNT, via a generate loop
```

`defines.sv` is generated by `ivd-gv` (structs `instruction_t`, `buf_inst_t`, `pe_inst_t`, all the widths, and
`vector_decoder`). The staff testbenches reach into the design **by name**, so `top.sv` must have signals called
`pe_inst_valid` and `buf_inst_valid`, the buffer instance must be `u_buffer`, and inside it the SRAMs stay
`u_matrix_mem`, `u_vector_mem` and `u_output_mem`.

### The timing contract

This is one valid design. It's the one our tools assume by default, and every check reports what it actually saw, so
a different choice shows up clearly rather than as a mystery. **The key fact:** the SRAMs are synchronous. An address
presented in cycle *t* gives its data in cycle *t+1*.

| Cycle | Controller | Buffer | PE |
|---|---|---|---|
| *t* | presents repetition *r*'s `buf_inst` (`buf_inst_valid`=1) | READ: drives the MEM0/MEM1 addresses. WRITE: remembers it | (still doing repetition *r−1*) |
| *t+1* | presents repetition *r*'s `pe_inst` (`pe_inst_valid`=1), i.e. a **1-cycle-delayed copy**; meanwhile `buf_inst` is already *r+1* | READ data for *r* is on `matrix_data`/`vector_data` all cycle. The MEM1 lane select uses the offset **and mode registered at *t***. A WRITE from *t* commits at the end of *t+1* with `output_data` as it is during *t+1* | computes *r* from this cycle's operands and updates acc/out **at the end of *t+1*** |

Why each rule exists (each one is a trap we reproduced tonight with a deliberately broken copy; see "Traps" below):
- **PE runs one cycle after its memory op:** that's when the read data exists. A PE fed in cycle *t* uses the previous
  repetition's data.
- **The lane select uses the registered mode:** NOP and WRITE carry mode field 0 (INT8), and by cycle *t+1* the
  controller already presents the next instruction. With the live mode, the last MAC of every INT16/INT32 run decodes
  its vector operand as INT8.
- **WRITE commits a cycle late:** the program is `…, NOP|OUT, WRITE|NOP`. OUT updates the output register at the end of
  its PE cycle, which is the WRITE's issue cycle. A WRITE that commits in its own issue cycle stores the pre-OUT value
  (zeros, right after CLR).
- **Zero bubbles:** issue a repetition every cycle, including straight from one instruction into the next
  (`inst_exec_begins` on the last repetition). Bubbles don't change results, but cycles enter the Part 3 FoM with
  exponent 2.3. Measured: one bubble per instruction costs +64 cycles at 16 PEs (16,504 vs 16,440 for INT8).

Module promises (each module's own check verifies exactly this, so we can build in parallel):
- **controller** (`make ctl-check`): every repetition of every instruction, in program order, one per cycle, with
  MemA/MemB offsets stepping by their increments; `pe_inst` = the same repetition's PE instruction one cycle later;
  `inst_exec_begins` high for exactly one cycle per instruction; both valids low when idle.
- **buffer** (`make buf-unit`): READ in cycle *t* → correct `matrix_data`/`vector_data` throughout *t+1*, whatever is on
  `buf_inst` in *t+1*. WRITE in *t* → `MEM2[MemAOffset]` = `output_data` of *t+1*. Nothing else changes MEM2.
- **processing_element** (`make pe-unit`): instruction and operands in cycle *t* → result after that cycle's edge. Every
  op in every mode per the spec; only OUT and CLR touch the output register; reset clears acc and out.
- **top** (`make eq`): wiring. PE *i* reads a 32-bit slice of the MEM0 word and writes **the same slice position** of
  the MEM2 word. The Python puts PE 0 in the most significant 32 bits.

Cycle model for this contract (matches every run tonight): `cycles = tiles × (cols + 3) + 8`, where
`tiles = ceil(rows / (PE_COUNT × lanes))`. At 16 PEs: **INT8 16,440, INT16 8,248, INT32 4,152**. That's 28,840 cycles,
57.7 µs at the 2 ns default clock. Treat this as the floor for Part 2.

### Traps we already hit (so you don't)

| Trap | Symptom | Caught by |
|---|---|---|
| OUT truncates instead of clamping | int8_test fails at once: **78% of its outputs clamp** (801/1024). int16/int32_test never clamp | `make pe-unit`, `make eq` (hint says "truncated") |
| Lane select with the live mode | **Passes all three official tests** (the INT16 vector ends in 0; the INT32 one ends in −1 = 0xFFFFFFFF) but is wrong | `make buf-unit`, `make eq-stress` |
| WRITE commits in its issue cycle | MEM2 words all zero | `make buf-unit`, `make eq` |
| PE instruction not delayed | int8 and int32 fail, int16 passes (vector ends in 0) | `make eq` |
| Controller runs Count instead of Count+1 | hangs or short runs | `make ctl-check` |
| `top.sv` names don't match the testbench | build error "unable to bind dut.pe_inst_valid" | every `make` target (with a hint) |
| Verilator + the staff SRAM model | Verilator at default optimization **skips the first instruction** of every program; the official tests can't see it (that instruction is a redundant CLR) | our flow defaults to Icarus; `SIM=verilator` uses `-fno-inline`; `make eq-both` |
| Environment | `AttributeError: 'Bits' object has no attribute 'length'` in `ivd-as` | `make setup PART=part2` pins `bitstring<5` |
| Part 3: fewer than 16 PEs | `ivd-as` **silently drops** instructions past the 128-entry IMEM; INT8 can't run at all below 5 PEs (`ivd-sim` overflows MemAOffset) | our scripts size the IMEM automatically |
| Part 3: deeper pipeline | the testbench dumps MEM2 one cycle after both valids go low (even a zero-width glitch counts), so a late WRITE is lost | keep a valid high until the last WRITE commits |

## The split

### Reasoning

- **Split the typing, not the understanding.** Each module has an **author** and a **defender**. The defender reviews
  the PR and must be able to explain every line out loud before it merges (the "teach-back rule"). In the oral exam
  you'll be asked about code you didn't write. Assume the examiner will pick exactly that.
- **Cross-assignment.** Build what you understand least, because building is how it sticks. Ryan wrote all three Part 1
  Python modules (git history), so the partner should write the RTL **PE**: the arithmetic spec becomes theirs by
  implementing it. Ryan takes the **controller and buffer**: cycle timing is new to both of us. In Part 3 we **swap
  domains**: the PE author takes system-level work, and the controller/buffer author takes the datapath, which means
  modifying the other person's PE. By Dec 3 each of us has built one datapath piece and one control piece and
  defended the others.
- **Pair on the moments that matter most:** the contract session (#1), top-level integration and the first
  equivalence run (#2), the first synthesis plus reading the reports together (#3), and the Part 3 strategy session
  (#4). Everything else runs in parallel, and the contract plus per-module checks make that safe.
- **Everyone runs everything once:** VCS, DVE, Design Compiler, the report files. "How did you verify it?" and "what
  was your critical path?" are near-certain questions, and "my partner ran that" is a bad answer.
- **Catch-up for Part 1:** whoever didn't write the Python spends an hour with `docs/walkthrough.html` and
  `docs/oral-prep.html` (Part 1 bank). The Part 2 PE is the same arithmetic.

**Planning numbers measured tonight** (details and the calculator in `docs/part3-ppa.html`):
- **Cycles:** all three tests have `tiles = ceil(256/P)`, so total cycles = `1801 × ceil(256/P) + 24` (exact for every P
  measured, 4–128). Only some PE counts reduce `tiles`: **16, 18, 19, 20, 22, 24, 26, 29, 32, 37, 43, 52, 64, 86, 128**.
  In between you pay area for nothing (43 and 48 PEs give identical cycles).
- **Bubbles:** one idle cycle per instruction costs about +1.5% FoM; two cycles per repetition costs ×4.9.
- **Area ballparks** (Yosys + open Nangate45, *not* DC; re-measure with `make synth`): a 32×32 signed multiplier ≈ 4.9k µm²,
  the naive PE's seven multipliers ≈ 9.0k µm², four 17×17 multipliers ≈ 6.4k µm², a naive PE ≈ 12–15k µm². So
  roughly 75 naive PEs fit under the 1,000,000 µm² cap, and multiplier sharing buys room for more.
- **IMEM:** the default 128 entries suffice for P ≥ 9; P = 5–8 need 256 (our scripts size it; the staff Makefiles
  don't); INT8 can't run below 5 PEs.
- **Leakage** in this library (typical corner) is about 15–27 nW/µm², so a 300k µm² design leaks roughly 5–8 mW.
  Area shows up in the power term too.
- **Clock power:** a DFFR_X1 clock pin costs about 9.6 fJ per cycle, so the 1,536 PE flops alone burn about 7.4 mW at
  2 ns, every cycle, whether or not their value changes. That is what clock gating removes.

## Part 4 (optional)

Extra credit, worth +5% of the project component, due **Tue Dec 1 11:59 PM, with no late days**. The handout is
`handouts/Project_Part_4.pdf`, and `part4/README.md` is the staff's own markdown copy of it. **Start it only after the
Part 3 report is drafted.** Decide go/no-go at the Part 3 strategy session, or by Sat Nov 28 at the latest.

**What it is.** The same accelerator again, this time in C++/SystemC, which Catapult HLS turns into RTL. Ports, reset,
testbenches and HLS scripts are all given. There are three `TODO` blocks, and each one mirrors a piece of our Part 2 RTL:

| File (under `part4/cmod/Accelerator/`) | Mirrors | Natural owner |
|---|---|---|
| `ProcessingElement/ProcessingElement.h` | `processing_element.sv`: the same ops, but operands arrive by `Pop()` and OUT leaves by `Push()` | Partner |
| `MainBuffer/MainBuffer.h` | `buffer.sv`: READ/WRITE/NOP inside a loop that's already written | Ryan |
| `Accelerator.h` | `controller.sv` + `top.sv`: pop an instruction, issue its Count+1 repetitions to the buffer and PEs | Ryan |

The new idea is the Connections library: `Push`/`Pop` block, so a missing transfer deadlocks the simulation instead of
giving a wrong answer. The write-up's question ("how is control different?") is good oral-exam material either way.

**Where it runs.** On FarmShare only: not caddy, and not a laptop, because it needs Catapult's SystemC and Matchlib
headers under `/cad`. Log in to FarmShare, run `/farmshare/home/classes/ee/admin/software/bin/rhel8.sh`, clone this
repo, then `cd part4 && source setup.csh` (`setup.csh` is csh, so run `tcsh` first if your shell is bash). From there,

- per module: `make clean; make sim_test; ./sim_test` in each module's folder (or `make systemc_test` in `part4/`, which runs all three)
- `cd hls/Accelerator && make hls`: about 30 minutes

**Deliverables.** The `make submission` zip (the three headers plus the generated `concat_Accelerator.v`) and a

## First Design Compiler run: check these three things

1. **Did the logic survive?** In `runs/<tag>/area_report_hier`, every `g_pe[*]` PE instance should have several
   thousand µm² (a naive PE is roughly 10–15k µm² by Yosys estimate; 16 PEs ≈ 150k, which matches the staff's
   `TARGET_AREA=150000`). The SRAMs are empty modules and `top` has no outputs, so a tool may delete logic whose only
   loads are those empty pins: Yosys does exactly that (0 cells; see `docs/synthesis.html`, Black boxes). If DC does
   too, ask on Ed before patching anything. The usual remedy is `set_dont_touch` on the memory instances before `compile_ultra`.
2. **Did DesignWare load?** `dc_synth.tcl` points `dw_foundation.sldb` at `/cad/synopsys/syn/M-2016.12-SP2/...`
   while `load_modules.sh` loads DC S-2021.06-SP5-4. Look for "Cannot find" / unresolved-library messages in
   `compile.log`.
3. **Did it fail quietly?** The staff Makefile pipes DC through `tee`, so `make` "succeeds" even when DC errors out (the
   same goes for `check_results.sh` in the equivalence tests). `make synth` counts error lines in `compile.log` for you.
