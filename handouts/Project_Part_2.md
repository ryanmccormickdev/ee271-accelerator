## 1 Introduction

For the EE271 class project, you will be working on a Single Instruction Multiple Data (SIMD) accelerator for matrix
multiplication. This project is segmented into three components. In the first component you will complete a Python
simulator of the accelerator. In the second component of the project you will complete an RTL implementation of the
accelerator using the lessons learned from completing the Python simulator and synthesize your RTL implementation in
order to determine its power performance and area (PPA). In the third component of the project you will optimize your
RTL implementation in order to improve its PPA.

This document will focus on the details/instructions needed to complete the second component of the project, which we
have labeled Assignment #2. **Please read the entirety of this document prior to starting the assignment.** If you need
a refresher on how to setup your environment or the overall structure of the accelerator, please refer to the previous
assignment. Section 2 will cover what needs to be done to finish the assignment as well as how to submit the assignment
once your implementation is complete.

## 2 Assignment #2

This assignment is broken into three components, completing the Verilog, verifying the Verilog against the simulator,
and synthesizing the Verilog. When completing these components you don't have to worry about efficiency functional
Verilog will get full points. The focus of assignment three will be on optimization. To access the code for this
project, use the command below:

```
$ git clone git@code.stanford.edu:EE271/simd-part2.git
$ cd simd-part2
```

To set up your conda environment, you can either use the one from part 1 of the project or just set up a new conda
environment using the following commands:

```
$ conda env create -p ee271-conda-env-p2 -f requirements.yml -vv
$ conda activate ./ee271-conda-env-p2
```

### 2.1 Functional Verilog

The first portion of the assignment focuses on implementing the SIMD accelerator in Verilog. For this section all the
files you need are located in the `unoptimized_verilog` folder. Within this folder, the files you will be editing are
located in the `logical` directory. Each module that you need to edit contains the phrase "Your Code Here".

In order to test your implementations, we have provided the `validation` directory. For your convenience we have
included test benches to test each module separately under the `testbenches` directory. These test benches will only
exercise the modules. It is up to you to determine if the module does what you expect. To run these test benches use
the commands seen below.

```
$ make compile TB_NAME=pe
$ make run_sim
```

To run a test bench for another module simply pass the relevant test bench name to the `TB_NAME` parameter when running
make. Additionally, feel free to edit these test benches as you see fit in order to debug your Verilog implementations.
Additionally, the make file provides the ability to view the waveforms generated by the simulation using the
`make debug` command.

Note that within each file you have access to a verilog file called `defines.sv`. This contains a variety of modules and
parameters you might find useful when writing your implementation. For example there is a module called
`vector_decoder` which will take the address passed to the vector memory as well as the current operating mode (INT8,
INT16, or INT32) and properly generate the desired output which should be sent to the PEs. The `defines.sv` file is
automatically generated when compiling the design through `make compile`.

### 2.2 Equivalence Testing

Once you think your Verilog is correct you can move on to verifying it against the supplied Python reference in
`simulator/src`. To do this, enter the equivalence testing directory. Once inside this directory you can run each of the
three tests to verify the functionality of your Verilog implementation.

```
$ make int8_test
$ make int16_test
$ make int32_test
```

If any of these tests fail you can try to diagnose the cause by debugging the wave form. Viewing the waveform can be
accomplished through using the command `make debug`.

### 2.3 Preliminary Synthesis

Once you have verified that your Verilog implementation is equivalent to the simulator you can now synthesize the
design. To accomplish this enter the `unoptimized_verilog/synth` directory. Once in this directory run
`make synthesize`. This will invoke Synopsys Design Compiler to synthesize your design. The results of the synthesis do
not matter too much, just make sure that the `compile.log` file is free of errors, warnings are fine.

### 2.4 Submission

To receive full credit, you must meet the following criteria.

1. Your Verilog implementation must satisfy the updated Part 1 arithmetic specification and pass all equivalence tests.
   (`int8_test`, `int16_test`, and `int32_test`)
2. Your `compile.log` file must be error free.

Once you believe you meet both of the above requirements you can generate a zip file for submission by running the
following at the top-level of the git repository:

```
$ make generate_submission
```
